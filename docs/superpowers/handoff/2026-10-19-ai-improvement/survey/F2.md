## 4. Feasibility arithmetic (my estimate from summary.md:157-159)
- At 188 tok/s prompt and 31 tok/s generation, one qwen ko call of 17,958 input tokens spends about 95 s on prompt alone. Generation then has about 25 s, roughly 800 visible-plus-hidden tokens.
- Each sub-call must fit: input/188 + output/31 < 120 s. For a 6,000-token input this leaves about 2,700 output tokens.
- Sending the full context to each of three sub-calls would triple prompt time. Each sub-call should get only what it needs (facts: known_facts; threads: open_threads; relations: entry names). The per-component input sizes are not recorded, so this must be measured.
- Splitting the calls does not by itself shorten total work, and the local server may not serve concurrent requests (not verified).

WHAT COULD REGRESS
1. Time limit (largest risk). Splitting into 3 calls only helps if each call finishes in 120 s. The qwen single call took 1,020 s with about 13.5k output tokens (qwen3.8-27b-ko.md:335). So the split alone probably will not meet the limit on qwen; F4 (effort lower) and possibly more parts are needed. The facts part also carries the full manuscript input (prefill time).
2. Concurrency cap. MAX_RUNNING_RUNS = 3 (run.ts:23, 221-224). chapter-check already runs continuity plus extraction in parallel (162-204). Three extraction parts in parallel plus continuity makes 4 running runs, and the 4th throws CONFLICT. Parallel fan-out must be at most 2 extraction parts beside continuity, or run in sequence. 3. Token budget. Each part resends the manuscript and context, so input tokens roughly triple for extraction. The daily cap (3,000,000 default, run.ts:20) is per user and counts every run, including failed ones (run.ts:122-126).
4. Partial failure. If part 2 fails (timeout or CONFLICT) after part 1 has billed, a retry re-bills part 1 unless partial results are kept. imports.ts:303-307 releases the whole claim on CONFLICT.
5. Timeout per part. The import override of 240 s (imports.ts:288) must be carried to every part, or import silently drops to 120 s. chapter-check uses the default 120 s.
6. Prompt injection. buildPrompt must call neutralizeDeep on every part's input (as chapter-extract.ts:39 does), and each system prompt must include TAG_DATA_RULE (chapter-extract.ts:35). 8. Cross-part consistency. Facts own summary and entries. Relations can name entries created in the same chapter (extraction-rules.ts:22-23 and chapter-extract.ts:32), so the relations part needs the facts part's entry names, which forces facts before relations. Facts and threads can run in parallel. supersedesFactRef (F refs) and existingThreadRef (T refs) must use the same ref lists for all parts (chapter-check.ts:152-160, 155-160).
9. Eval metrics. eval-client.ts:440-452 records productTimeoutMs and wouldTimeOut per task name. Renaming or splitting tasks changes what the 2026-10-18 timing table means, so a new baseline is needed.
10. Interview extraction (extraction.ts header, T12) shares ExtractionSchema. Changing the shared schema affects interview extraction.
