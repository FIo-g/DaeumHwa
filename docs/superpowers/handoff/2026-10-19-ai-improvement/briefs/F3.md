# Brief F3 (local branch): reader simulation, one call per persona

Implementer: haiku, TDD, isolated worktree. Read CLAUDE.md first. All paths are repo-relative. Verified against code on `main` (2026-10-19).

## Goal

`runReaderSimulation` currently makes ONE `generateObject` call with all 4 personas (maxTokens 16000, medium effort, 120 s default limit). On slow local models that call blows the 120 s product limit. Split it into one call per persona, run the calls concurrently, and merge them back into ONE `ReaderSimResult` stored in ONE `ai_runs` row. Public signatures, route, action, UI, stored output shape, interview digest and results page stay unchanged.

Scope note: the product path (`src/ai/index.ts`) only builds `OpencodeAiClient` or `AnthropicAiClient`. `OllamaAiClient` is used only by `eval/novel/models.ts`, and the eval harness calls `runReaderSimulation` directly (`eval/novel/steps/chapter.ts:366`), not through the route. So production never runs a local provider today: the local serial default and its wall-time question apply only to the eval harness, and the route `maxDuration = 300` does not apply to that run (it would apply only if a future product path used Ollama). The cloud parallel path is what production gets.

## Design (ordered)

1. `src/ai/run.ts`: extract `function resolveTimeoutMs(meta: AiRunMeta, task: { timeoutMs?: number }): number { return timeoutOverrideMs ?? meta.timeoutMs ?? task.timeoutMs ?? DEFAULT_AI_TIMEOUT_MS }` and use it in `runAiTask` (line 93). Behavior must not change (existing tests in `run.test.ts` "cancel and timeout" and "setAiTimeoutOverride" must still pass).
2. `src/ai/run.ts`: add `export async function runAiTaskSplit<I, O>(db, meta, task, parts, merge, client = getAiClient(), options?)`. Algorithm:
   a. `parts.length === 0` -> throw `AppError('VALIDATION', '실행할 항목이 없습니다.')` before anything is inserted.
   b. ONE `assertCanStartRun(db, meta.userId)` and ONE `insertRun(db, meta, task.name, taskModel ?? client.defaultModel)` (same as `runAiTask`). One row, one cap slot.
   c. `timeoutMs = resolveTimeoutMs(meta, task)`.
   d. `concurrency = options?.concurrency ?? splitConcurrencyFromEnv() ?? (isLocalProvider(client.provider) ? 1 : DEFAULT_CLOUD_SPLIT_CONCURRENCY)`, clamped to `1..parts.length`, with `const DEFAULT_CLOUD_SPLIT_CONCURRENCY = 2` (exported from `src/ai/run.ts`). `splitConcurrencyFromEnv()` reads `process.env.AI_SPLIT_CONCURRENCY` at call time; accepts only a positive integer string, otherwise returns `undefined`. `isLocalProvider(provider)` is true for `'ollama'` and `'eval:ollama'` (same selector F2 uses, EvalClient reports `eval:${inner.provider}`). DECISION (made here, not deferred to F4): local providers default to serial (1), cloud providers default to 2 in flight, and `AI_SPLIT_CONCURRENCY` overrides both. Reason for 2, not 4: four simultaneous calls per user per run risk provider rate limits (429, overloaded), and `MAX_RUNNING_RUNS` counts runs, not calls, so it does not protect against that. Client retry check (done on `main`): `AnthropicAiClient` (`src/ai/anthropic.ts:305`) and `OpencodeAiClient` (`src/ai/opencode.ts:42`) both use SDK `maxRetries: 1`, so a 429 gets one retry and then fails the whole run (all-or-nothing). A cap of 2 halves the burst; the cost is that 4 shards take about 2 shard times on cloud instead of 1. The local eval and operators therefore need NO env setting; F4 does not have to set anything.
   e. Create `const abortSiblings = new AbortController()`. For each part run `runPart(i)`:
      - skip (return) if `failure` is already set or `meta.signal?.aborted`.
      - The WHOLE body of `runPart` after the skip check is inside one try/catch: `task.buildPrompt(part)`, `callSignals`, `generateObject`, `postProcess`, usage accounting and the `onPart` call. Any error, including a synchronous throw from `buildPrompt` or `postProcess`, goes through the same failure path below (so `Promise.all` never rejects early, siblings are aborted, and the single row is always finished). This mirrors `runAiTask`, which has `buildPrompt` inside its try block.
      - per-part signals: `const { signal, deadline } = callSignals({ ...meta, signal: meta.signal ? AbortSignal.any([meta.signal, abortSiblings.signal]) : abortSiblings.signal }, timeoutMs)`. The deadline starts when the part starts, so waiting for a free worker slot does not consume the part's 120 s. Declare `deadline` outside the try (`let deadline: AbortSignal | undefined`) so the catch can use it.
      - `client.generateObject({ task: { name: task.name, input: part }, system: task.system, prompt: task.buildPrompt(part), schema: task.schema, effort: task.effort, maxTokens: task.maxTokens, model: taskModel, signal, timeoutMs })`.
      - on success: add `result.usage` to the total, `outputs[i] = task.postProcess ? task.postProcess(result.object, part) : result.object` (each part post-processed against ITS OWN input), remember `result.model` of part 0.
      - on error: add `usageFromError(error)` to the total; if `failure` is not set, set `failure = toRunError(error, meta.signal, deadline)` and call `abortSiblings.abort()`. `deadline` is the one from THIS part's own `callSignals` call (not a shared one); if the error happened before `callSignals` ran (for example `buildPrompt` threw), `deadline` is undefined and `toRunError` must be called with a fresh never-aborting signal (for example `new AbortController().signal`) so it is classified as a plain `AI_ERROR`. A sibling abort caused by `abortSiblings.abort()` after a first failure must never replace `failure`. `runPart` never throws: the catch block itself only does synchronous bookkeeping.
   f. Worker pool: `Math.min(concurrency, parts.length)` workers pull the next index from a shared counter until parts run out. `await Promise.all(workers)`.
   g. After the pool: if `meta.signal?.aborted && !failure` set `failure = cancelledError()`. If `failure`: `finishRun(db, runId, { status: 'error', error: failure.message, usage: total })` and `throw failure`.
   h. Else `output = merge(outputs, parts)` inside try/catch (a throw becomes `toRunError`, finished as error). Then re-check `meta.signal?.aborted` -> cancelled. Then `finishRun(db, runId, { status: 'done', usage: total, model, output })` and return `{ output, runId }`.
   i. Failure policy: all-or-nothing (same as today). Unstarted parts are not run after a failure; running siblings are aborted.
   j. Optional `options.onPart?: (info: { index: number; elapsedMs: number; ok: boolean }) => void`, called once per finished part (success or failure) with the wall time of that call. It exists so a later local measurement can read per-call time without `eval/novel/eval-client.ts`. Call it from `runPart` right after each `generateObject` settles (use `Date.now()` before and after). Errors thrown by the hook are swallowed.
3. `src/ai/tasks/reader-sim.ts`: add `splitReaderSimInput(input)`: returns `input.personas.map((p) => ({ ...input, personas: [p] }))` (same chapter text, summaries, work for each part; order = input order). Empty personas -> `[]`.
4. `src/ai/tasks/reader-sim.ts`: add `mergeReaderSim(outputs: ReaderSimResult[]): ReaderSimResult`. `personas` = concatenation in `outputs` order; if a `personaId` repeats, keep the first and drop later ones. `summary` = the distinct non-empty trimmed `summary` strings joined with `'\n'` (empty string if none). No extra AI call.
5. `src/server/ai-features.ts` `runReaderSimulation`: build the same input object as today, then `const parts = splitReaderSimInput(input)`; call `runAiTaskSplit(db, { userId, workId, chapterId, signal }, readerSimTask, parts, mergeReaderSim, client)`. Keep the signature, the empty-body check, `selectPersonas`, and `{ runId, result: output }` return. Import the two helpers and `runAiTaskSplit`; drop the now unused `runAiTask` import only if nothing else uses it (it is still used by `runDirectionAdvice` and `suggestStyleCard`, so keep it).
6. `src/test/ai-fakes/reader-sim.ts`: compute `const slot = READER_PERSONAS.findIndex((p) => p.id === persona.id)`; use `slot >= 0 ? slot : index` for `FAKE_RATINGS`/`FAKE_RISKS` (and the reaction offset). A full 4-persona call must produce exactly the same output as before.
7. Do not touch: `eval/novel/*`, route, action, panel, `interview.ts`, page, `READER_SIM_SYSTEM` (exact text is asserted in `reader-sim.test.ts:50-63` and localized in `eval/novel/localize/en-systems.ts:151`).

## Risks

- Local Ollama serializes requests; with full parallelism every shard timer could expire in the server queue. Mitigation: local providers default to concurrency 1 (`isLocalProvider`), `AI_SPLIT_CONCURRENCY` overrides; the per-part deadline only starts when the part starts, so our own pool never eats the budget. Production never uses a local provider today (see Goal scope note), so this applies to the eval harness only.
- Serial local run, eval harness only: 4 shards x up to 120 s is about 480 s of wall time per chapter. The route `maxDuration = 300` (`src/app/api/works/[workId]/chapters/[chapterId]/reader-sim/route.ts:8`) does not apply to the eval run; it would apply only if a future product path used Ollama. Not solved here and not tested; reported after the later measurement.
- Provider rate limits on the cloud path: parallel calls per user per run can hit 429 or overloaded errors. Both clients retry once (`maxRetries: 1`), then the run fails as a whole. Mitigation: cloud default concurrency is 2 (not 4), `AI_SPLIT_CONCURRENCY` overrides. `MAX_RUNNING_RUNS` counts runs, not calls, so it does not guard this.
- Per-persona prompts lose the cross-persona rule "같은 반응을 복사하지 않는다". Accepted; system prompt text is locked by tests and localization.
- Input tokens grow about 4x per chapter (manuscript sent per shard); counts toward the 3,000,000 daily limit. Usage is summed into the single row.
- Chapter `summary` is the join of per-persona summaries, so it may be longer and repetitive.
- Hidden regression: `runAiTask` refactor in step 1 (timeout expression); the existing `run.test.ts` suite guards it.
