## Goal

`runReaderSimulation` (`src/server/ai-features.ts:85`) currently makes ONE `runAiTask` call with all 4 personas (`readerSimTask`: maxTokens 16000, medium effort, no own `timeoutMs`, so the 120 s default applies). On slow local models that call is far over the 120 s product limit. Split it into one call per persona, run the calls concurrently, and merge them back into ONE `ReaderSimResult` stored in ONE `ai_runs` row. Public signatures, route, action, UI, stored output shape, interview digest and results page stay unchanged. `runAiTask` and `startAiStream` are NOT edited (spec 8: `runAiTaskSplit` does not change `runAiTask`); the split helper is new code next to them.

Scope note: the product path (`getAiClient()` in `src/ai/index.ts`) only builds `OpencodeAiClient` or `AnthropicAiClient`. `OllamaAiClient` is used only by `eval/novel/models.ts`, and the eval `reader` step (`eval/novel/steps/chapter.ts:596-607`) calls `runReaderSimulation(ctx.db, ctx.actor, { chapterId }, ctx.client)` directly (line 601, inside `guarded`), not through the route. So production never runs a local provider today: the local serial default and its wall-time question apply only to the eval harness, and the route `maxDuration = 300` does not apply to that run. The cloud parallel path (2 in flight) is what production gets.

Eval fact (matters for the numbers below): the eval does NOT enforce 120 s. `eval/novel/run.ts:127` calls `setAiTimeoutOverride(profile.timeoutMs)` (local 3,600,000 ms, cloud 900,000 ms, `eval/novel/models.ts:35-36`); `timeoutOverrideMs` wins over every other limit (`src/ai/run.ts:93`). So in eval "over 120 s" is only the `wouldTimeOut` label on a `CallRecord`, and `runAiTaskSplit` must honor the same override for each part. Also `guarded`/`withModelRetry` (`eval/novel/steps/util.ts:66-126`) retries the whole `runReaderSimulation` once on a model failure, so a failed split run is re-run in full (up to 8 shard calls); `state.retried['chN:reader']` counts it.

## Design (ordered)

1. `src/ai/run.ts`: add private `function resolveSplitTimeoutMs(meta: AiRunMeta, task: { timeoutMs?: number }): number { return timeoutOverrideMs ?? meta.timeoutMs ?? task.timeoutMs ?? DEFAULT_AI_TIMEOUT_MS }`, the same precedence as `runAiTask` (line 93). `runAiTask` itself is not refactored to use it (spec 8, and it keeps the merge with later cloud changes to `run.ts` trivial). A test (7) pins the precedence.
2. `src/ai/run.ts`: add `export async function runAiTaskSplit<I, O>(db, meta, task, parts, merge, client = getAiClient(), options?)`. Algorithm:
   a. `parts.length === 0` -> throw `AppError('VALIDATION', '실행할 항목이 없습니다.')` before anything is inserted.
   b. ONE `assertCanStartRun(db, meta.userId)`, then `const taskModel = task.model?.()` and ONE `insertRun(db, meta, task.name, taskModel ?? client.defaultModel)` (same order as `runAiTask`, `:89-91`). One row, one cap slot.
   c. `timeoutMs = resolveSplitTimeoutMs(meta, task)`.
   d. `concurrency = options?.concurrency ?? splitConcurrencyFromEnv() ?? (isLocalProvider(client.provider) ? 1 : DEFAULT_CLOUD_SPLIT_CONCURRENCY)`, clamped to `1..parts.length`, with `const DEFAULT_CLOUD_SPLIT_CONCURRENCY = 2` (exported from `src/ai/run.ts`). `splitConcurrencyFromEnv()` reads `process.env.AI_SPLIT_CONCURRENCY` at call time; accepts only a positive integer string, otherwise returns `undefined`. `isLocalProvider(provider)` is true for `'ollama'` and `'eval:ollama'` (`OllamaAiClient.provider` is `'ollama'`, `src/ai/ollama.ts:179`; `EvalClient` reports `eval:${inner.provider}`, `eval-client.ts:323`; `FakeAiClient` is `'test'` and counts as cloud; F2 compares the same two strings inline, it does not import this). DECISION (made here, not deferred to F4): local providers default to serial (1), cloud providers default to 2 in flight, and `AI_SPLIT_CONCURRENCY` overrides both. Reason for 2, not 4: four simultaneous calls per user per run risk provider rate limits (429, overloaded), and `MAX_RUNNING_RUNS` counts runs, not calls, so it does not protect against that. Client retry check (re-verified on the local tip): `AnthropicAiClient` (`src/ai/anthropic.ts:305`) and `OpencodeAiClient` (`src/ai/opencode.ts:42`) both use SDK `maxRetries: 1`, so a 429 gets one retry and then fails the whole run (all-or-nothing). A cap of 2 halves the burst; the cost is that 4 shards take about 2 shard times on cloud instead of 1. The local eval and operators therefore need NO env setting; F4 does not have to set anything. (F4's `EvalClient` lane, if merged, also serializes local calls; the two layers agree and neither depends on the other.)
   e. Create `const abortSiblings = new AbortController()`. For each part run `runPart(i)`:
      - skip (return) if `failure` is already set or `meta.signal?.aborted`.
      - The WHOLE body of `runPart` after the skip check is inside one try/catch: `task.buildPrompt(part)`, `callSignals`, `generateObject`, `postProcess`, usage accounting and the `onPart` call. Any error, including a synchronous throw from `buildPrompt` or `postProcess`, goes through the same failure path below (so `Promise.all` never rejects early, siblings are aborted, and the single row is always finished). This mirrors `runAiTask`, which has `buildPrompt` inside its try block.
      - per-part signals (`callSignals` is the private helper at `run.ts:68`): `const { signal, deadline } = callSignals({ ...meta, signal: meta.signal ? AbortSignal.any([meta.signal, abortSiblings.signal]) : abortSiblings.signal }, timeoutMs)`. The deadline starts when the part starts, so waiting for a free worker slot does not consume the part's limit (120 s in product, the profile limit in eval). Declare `deadline` outside the try (`let deadline: AbortSignal | undefined`) so the catch can use it.
      - `client.generateObject({ task: { name: task.name, input: part }, system: task.system, prompt: task.buildPrompt(part), schema: task.schema, effort: task.effort, maxTokens: task.maxTokens, model: taskModel, signal, timeoutMs })`.
      - on success: add `result.usage` to the total, `outputs[i] = task.postProcess ? task.postProcess(result.object, part) : result.object` (each part post-processed against ITS OWN input), remember `result.model` of part 0.
      - on error: add `usageFromError(error)` to the total; if `failure` is not set, set `failure = toRunError(error, meta.signal, deadline)` and call `abortSiblings.abort()`. `deadline` is the one from THIS part's own `callSignals` call (not a shared one); if the error happened before `callSignals` ran (for example `buildPrompt` threw), `deadline` is undefined and `toRunError` must be called with a fresh never-aborting signal (for example `new AbortController().signal`) so it is classified as a plain `AI_ERROR`. A sibling abort caused by `abortSiblings.abort()` after a first failure must never replace `failure`. `runPart` never throws: the catch block itself only does synchronous bookkeeping.
   f. Worker pool: `Math.min(concurrency, parts.length)` workers pull the next index from a shared counter until parts run out. `await Promise.all(workers)`.
   g. After the pool: if `meta.signal?.aborted && !failure` set `failure = cancelledError()` (private, `run.ts:353`; `finishRun` `:297`, `usageFromError` `:333`, `toRunError` `:357`, `insertRun` `:273` are all private to `run.ts`, which is why the helper lives there). If `failure`: `finishRun(db, runId, { status: 'error', error: failure.message, usage: total })` and `throw failure`.
   h. Else `output = merge(outputs, parts)` inside try/catch (a throw becomes `toRunError`, finished as error). Then re-check `meta.signal?.aborted` -> cancelled. Then `finishRun(db, runId, { status: 'done', usage: total, model, output })` and return `{ output, runId }`.
   i. Failure policy: all-or-nothing (same as today). Unstarted parts are not run after a failure; running siblings are aborted.
   j. Optional `options.onPart?: (info: { index: number; elapsedMs: number; ok: boolean }) => void`, called once per finished part (success or failure) with the wall time of that call. It exists so a later measurement can read per-call time without `eval/novel/eval-client.ts` (the eval already records one `CallRecord` per shard). Call it from `runPart` right after each `generateObject` settles (use `Date.now()` before and after). Errors thrown by the hook are swallowed.

## Risks

- Local Ollama serializes requests; with full parallelism every shard timer could expire in the server queue. Mitigation: local providers default to concurrency 1 (`isLocalProvider`), `AI_SPLIT_CONCURRENCY` overrides; the per-part deadline only starts when the part starts, so our own pool never eats the budget. Production never uses a local provider today (see Goal scope note), and the eval's own limit is 3,600,000 ms, so this applies to the eval harness only and only as accounting (`durationMs` with queue wait).
- Serial local run, eval harness only: 4 shards x up to 120 s is about 480 s of wall time per chapter. The route `maxDuration = 300` (`src/app/api/works/[workId]/chapters/[chapterId]/reader-sim/route.ts:8`) does not apply to the eval run; it would apply only if a future product path used Ollama. Not solved here and not tested; reported after the later measurement.
- Provider rate limits on the cloud path: parallel calls per user per run can hit 429 or overloaded errors. Both clients retry once (`maxRetries: 1`), then the run fails as a whole. Mitigation: cloud default concurrency is 2 (not 4), `AI_SPLIT_CONCURRENCY` overrides. `MAX_RUNNING_RUNS` counts runs, not calls, so it does not guard this.
- Per-persona prompts lose the cross-persona rule "같은 반응을 복사하지 않는다". Accepted; system prompt text is locked by tests and localization.
- Input tokens grow about 4x per chapter (manuscript sent per shard); counts toward the 3,000,000 daily limit. Usage is summed into the single row.
- Chapter `summary` is the join of per-persona summaries, so it may be longer and repetitive.
- Hidden regression: none expected in `runAiTask` (not edited). The risk moves to the new timeout precedence copy, pinned by test 7.
- Eval retry multiplies cost: `withModelRetry` re-runs the whole simulation once on a model failure, so a failing local run can spend 8 shard calls (all-or-nothing, open question 3).
- Product behavior change: unlike F1 and F2 (provider-gated), F3 changes the product path itself (4 calls per run, 2 in flight, about 4x input tokens). The plan's local gate says "no local-only behavior leaks into the product path"; F3 is not local-only by design (production gets the cloud parallel path), so the reviewer must confirm that is intended (open question 6).
