## Goal

On local models (Ollama) one `chapter-extract` call is too slow for the 120 s product timeout. Add a split mode that runs three smaller structured calls one after another (facts, threads, relations), merges them into the same `Extraction` shape, and plugs into `runChapterCheck`. Cloud providers keep the single call. Scope note: in the product, `getAiClient()` (src/ai/index.ts:15-17) returns only `AnthropicAiClient` or `OpencodeAiClient`, so provider `'ollama'` never occurs there. The split therefore runs by default only in the eval harness (`eval:ollama`) or when `AI_EXTRACT_SPLIT=on` is set; product behavior is unchanged unless that env var is set, and the product path has no Ollama client. The import path is NOT split (it keeps one call and its 240 s limit, so MVP F6 "회차당 AI 호출 1회" stays true).

Decisions already made (do not re-open): new task names per part; parts run sequentially (facts, then threads, then relations); the facts part owns `summary` and `entries`; relations get the entry names the facts part created; `sourceRef` = facts run id; no DB migration; no new package; `extractionToProposals` unchanged.

## Evidence (numbers, from docs/eval/novel/2026-10-18)

- qwen ko, one chapter-extract call: 1,020 s `durationMs`, 17,958 in / 13,532 out tokens (qwen3.8-27b-ko.md:335). Product limit 120 s. The 1,020 s includes queue wait behind the parallel continuity-check (the eval client stamps the start before the call is sent and the 2026-10-18 data has no `queueMs`; see F4 brief). Pure compute from the speeds below is about 17,958/188 + 13,532/31 = 95 + 437 = about 532 s. Do not read 1,020 s as pure call time. Even 532 s is far over 120 s.
- qwen en: 1,848 s, 21,205 in / 27,139 out (qwen3.8-27b-en.md:174).
- Cloud: haiku ko 54.5 s, haiku en 25.6 s, luna ko 48.1 s, luna en 80.8 s. Cloud is inside the limit, so cloud stays single-call.
- Local speed: ~188 tok/s prompt, ~31 tok/s generation (summary.md:159-160: ko 188.34 prompt / 30.83 gen tok/s; en 175.08 / 29.47). The ~188 and ~31 figures are the ko values. A part fits the limit only if input/188 + output/31 < 120 s. Worked example for qwen ko, the 17,958-token input of the single call: prefill alone is about 95 s per part (each part resends the manuscript), which leaves about 25 s, roughly 780 output tokens. A part with 3,000 output tokens would take about 95 + 97 = 190 s. So splitting alone is NOT expected to bring every part under 120 s for a chapter this long; it is expected to pass only when `input/188 + output/31 < 120` holds, for example about 13,500 input tokens with 1,500 output tokens (72 + 48 s). Facts `maxTokens` is 8000 (up to about 258 s of generation), so nothing enforces a small output; the per-part output size is a measured target, not a guarantee. The part prompts omit unused blocks (known_facts, open_threads), so threads and relations inputs are smaller than 17,958, but how much smaller is unmeasured.

## Risks

- Each part resends the manuscript, so input tokens for extraction roughly triple on local (daily cap 3,000,000, src/ai/run.ts:20). A local server with 188 tok/s prompt speed spends ~95 s on an 18k-token prompt, so a part may still pass 120 s if the manuscript is long. The split removes output time, not prefill time. If the next measurement still shows timeouts, chunk the manuscript (follow-up, not this track).
- Part `maxTokens` (8000/4000/4000) are guesses; a cap that is too low causes a truncation error. Check against the next local run. Decision: keep them as written in this track (no truncation test, no lower cap); facts at 8000 allows about 258 s of generation, so a facts part can still pass 120 s. Lowering facts to about 3,000 with a truncation test is an option for the next round if the measurement shows runaway output.
- Facts-before-relations is required (relations need the new card names), so no parallelism between those two. Threads could run in parallel with facts, but local Ollama serves one request at a time, so sequential is chosen.
- If the relations part fails after facts and threads were billed, the whole chapter check fails and a rerun re-bills them (no partial-result storage).
- Eval byTask tables now show three task names instead of `chapter-extract`, so the 2026-10-18 timing table is not directly comparable. Compare by summing the three.
- `maxDuration = 300` on the check route: three sequential 120 s parts plus the parallel continuity call can exceed it on a very slow server. Not fixed here.
