# F4. Local server serialization and helper think switch (LOCAL branch)

## Goal

Two eval-harness changes for local (Ollama) models, plus honest accounting:

1. Never run two AI calls at once against one local server. Today continuity-check and chapter-extract run together (Promise.allSettled in `runChapterCheck`), so one waits behind the other inside Ollama, and the waiting time is counted as call time.
2. Add a switch to run helper tasks (every AI task except `draft-chapter`) with a lower `think` setting, so a compare run can test the hypothesis that less thinking keeps helper quality and cuts time.

Terminology: in this track "effort" (as in the follow-up doc's F section) means Ollama's `think` setting for helper tasks. `AiEffort` is not forwarded to Ollama and must not be wired in or changed.

Both changes live in the eval harness and in the Ollama client. The product path (`src/server/chapter-check.ts`, `src/ai/run.ts`) is NOT changed. Product code never builds `OllamaAiClient` (only `eval/novel/models.ts` does), so no product behaviour changes.

Ollama runs with `OLLAMA_NUM_PARALLEL=1` (README.md:42-48), so the parallel pair queues inside Ollama and total time does not change; only the accounting changes.
- The concurrent pair: `src/server/chapter-check.ts:163-204` (two `runAiTask`, one sibling AbortController). The eval step `check` (`eval/novel/steps/chapter.ts:263-278`) calls it with `ctx.client` (the EvalClient). The eval step `continuity` makes no AI call.

- Slow single calls remain after serialization (README.md:125: proofread 45 min, continuity 21 min on qwen). Serialization alone will NOT bring these under 120 s. Only less thinking or less work does.

Pattern: `const prev = this.lane; let release!: () => void; this.lane = new Promise<void>((r) => (release = r)); await prev; return release`.

Keep the existing synchronous-throw handling. ## Risks

- Lock is per EvalClient (per process, per run dir). Two runs against one Ollama still contend; the existing worker lock (`eval/novel/worker-lock.ts`) is per run dir only. Out of scope; the novel-eval skill should keep one local model running at a time (model-setup.md:30).
- `think: false` on gpt-oss is ignored by Ollama (it needs a level). `checkHelperThink` rejects `off` there, so a run never records a `thinkRequested: false` that was not applied. Docs say use `low` there. Non-Ollama profiles and exaone reject `--helper-think` for the same reason (nothing to apply).
- Moving `prepare()` after the lock changes `seq` order to lock order. Call files are named by seq, so numbering stays unique and increasing; only which parallel call gets the lower seq may differ from before.
- A queued call whose sibling aborted: the lane wait is raced against `args.signal`, so it stops waiting at once and is recorded as a failed call (same as before). Its lane slot is released only after the head call ends, so later calls still wait for the head call (up to the 3,600,000 ms local timeout); only the aborted call itself stops early.
- Lower think may hurt helper accuracy (unverified). Default stays unchanged, so existing runs and baselines are not affected.

## Open questions

- Should serialization also apply to the product `runChapterCheck` when a future local provider ships? Decision for now: no, eval-only, gated on `profile.queue === 'local'`.
- Is `off` the right helper setting for qwen, or should a compare also try `low` (qwen3 accepts only true/false in Ollama)? Decided: qwen accepts only `off`; `low`/`medium`/`high` are rejected for boolean-think profiles.
- Cross-process lock for a shared Ollama: not built. Add only if two runs are ever launched together.
