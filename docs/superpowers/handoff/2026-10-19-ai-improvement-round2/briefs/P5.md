# P5. Mark planned threads in the draft context and add one draft rule (APP, cloud and local)

STATUS: ready. The code does not do this today, and the spec design can be built as written. The evidence is thin, so say so in the results doc: in the six saved runs the planned-thread leak shows up in 1 of 8 saved chapter-1 draft outputs, and that one was a rejected attempt (details under Evidence). One design choice the spec leaves open is fixed here: the mark is printed only for the draft prompt, through an option on `renderContextPack`, so the continuity-check prompt stays byte-identical.

Written against `feat/ai-improvement-round2` at 3a05674. Find code by symbol name; line numbers move. P4 edits the same draft system prompt in the same worktree and runs first. See Dependencies.

## Goal

A thread whose status is `planned` (not yet planted) must not leak into a draft unless the author's instructions bring it up. Two small prompt changes:

1. In the `<wiki>` block of the draft prompt, every `planned` thread line carries the label `지시에 있을 때만 쓴다` ("write only when the instructions say so").
2. `DRAFT_SYSTEM` gets one rule line that quotes that label and says what to do with it. The label alone is not enough: it sits inside a `<wiki>` data block, and `TAG_DATA_RULE` tells the model to ignore instructions found inside tags. The system rule is what carries the force.

Korean copy for the product, and an English twin for the eval's `--lang en` runs (scaffold rule, English system rule, English snapshot).

So every planned thread is always in the pack, whatever its target chapter. Sorted by importance, then overdue, then title; at most `MAX_THREADS` = 15.

## Gating

- No flag and no profile gate. The spec lists P5 as `app`: cloud and local drafts both get it. The cloud default path changes only by the two intended edits: the rule line in `DRAFT_SYSTEM` and the mark on planned threads in the draft's wiki block.
- The mark is requested at exactly one call site (`startDraft`). Every other consumer of `renderContextPack` (continuity check, `eval/run-continuity.ts`, the localize samples) keeps the default render, so their prompts and their pinned tests do not change. The "continuity prompt carries no mark" test protects this.
- `AI_SPEECH_STYLE` is not involved: the rule is not behind the speech flag. With the speech flag off the draft system is the new reference text from this track on.
- Local-only work (two-step, beats) is untouched except that the beat call sees the same marked pack, which is harmless: its system already says to use only the wiki and the author's instructions.

## Risks

- **Mixed effects in R2b.** P4 and P5 both change the cloud draft system prompt, so an R2b change in draft behaviour cannot be split between them (spec section 4 accepts this for P4's two rules). Say so in the results doc.
- **Over-suppression.** A model may now skip wiki facts that overlap a planned thread (for example the silver-coin debt appears both as a confirmed fact on Baek Jiwon and as planned thread T3). The rule only forbids the thread's events and information when the instructions do not mention it, and rule 1 already forbids uninstructed events, so the practical change is small. Watch Q1 and Q3 in R2b for flatter chapters.
- **Label read as a command.** The label sits in a data block under `TAG_DATA_RULE`. The quoted system rule is the mitigation; the drift test keeps the two strings in step.
- **Snapshot collisions with P4.** P4 and P5 both edit `DRAFT_SYSTEM`, `DRAFT_CHAPTER_SYSTEM`, the JSON snapshot, the `speech-off` inline snapshot and the `draft-chapter.test.ts` line list. Insert one line at the stated anchor each time and re-read the file before editing; never paste a whole regenerated snapshot.
- **Soft budget.** Up to 210 chars over the 12,000 pack budget on a draft prompt. Not worth a code path.
- **Thin evidence.** One rejected qwen attempt out of eight outputs. The change is one rule line and one label, which is why it is still worth doing; do not oversell it in the results.

## Open questions (default chosen)

- Mark every `planned` thread, or only those not yet due? Default: every `planned` thread. A thread targeted at this very chapter is still the author's call to bring up in the instructions, and a deterministic "due now" exception would be a second rule to explain and test.
- Should a thread whose title appears in the instructions lose the mark (code decides)? Default: no. Whether the instructions "mention" it is a judgement for the model, and keyword matching on Korean titles is fragile.
- Should `DRAFT_BEATS_SYSTEM` get the same rule? Default: no. P1 and P2 own draft-beats.ts, and the beat list is built from the instructions.
- Put the label inside the parenthesis, or at the end of the line after the description? Default: inside the parenthesis, after the status and target, so it is read with the status and the line prefix `- [Tn] name (` stays parseable by anything that reads it.
- Is `PLANNED_THREAD_MARK` better placed in a shared module so `draft-chapter.ts` can import it? Default: no, keep a literal in `draft-chapter.ts` and a drift test; importing `context.ts` would pull the DB layer into a pure prompt module.
