# M4. Task values next to sent values in every call record, and the `--product-limits` option (eval harness)

STATUS: ready. Half of the first sentence of the spec row already holds in code: the sent values are recorded today (`effortRequested` and `maxTokens` in `CallRecord`). What is missing is the task's own effort and maxTokens, the option, and a way to count cut-off calls for run R2l. This brief adds exactly those. Nothing in `src/` changes.

Written for branch `feat/ai-improvement-round2` at tip `3a05674` (round 1 merged: F4 lane, `thinkRequested`, `helperThink` all in). Find code by symbol name; line numbers move. Implement after M1, M2 and M3 and before M5 (see "Dependencies on other tracks").

## Goal

1. Every call record states two pairs of values: what the product task asks for (`taskEffort`, `taskMaxTokens`) and what the eval actually passed to the inner client (`effortRequested`, `maxTokens`, which already exist). Today only the sent pair is stored, so a reader cannot tell that the eval raised or replaced the task's values.
2. A run-level option `--product-limits` (eval CLI `init`, stored in `config.json`). When on, `EvalClient` passes the task's own `maxTokens` unchanged, with no profile floor. Effort is NOT changed by the option (user decision: cloud effort stays `high`, spec section 4).
3. A small summary block `outputCap` in `run-summary.json` that counts calls cut off by the output cap and calls whose output went over the task's own cap, so R2l can report "truncated drafts" and R2a/R2b can report how many calls the product cap would have cut.

The option is off by default. Without it the request sent to every inner client is byte-for-byte what it is today.

## Evidence (verified in code or in the saved runs)

Code facts:

- `EvalClient.prepare` (`eval/novel/eval-client.ts`) computes `maxTokens: Math.max(productMaxTokens, this.profile.maxTokensFloor)`. Floors in `eval/novel/models.ts`: 32000 for qwen, gpt-oss, haiku, luna and fake; 8192 for exaone (its context is 32768).
- `generateObject` and `streamText` in `EvalClient` pass `effort: this.profile.effort` and `maxTokens: call.maxTokens` to the inner client. `args.effort` and `args.maxTokens` (the task's values, set by `runAiTask`/`startAiStream`) are read only for `maxTokens`. The task effort is thrown away. Profile efforts: haiku and luna `high`, local profiles `max`.
- `settle` writes `effortRequested: this.profile.effort` and `maxTokens: call.maxTokens`. No record field holds the task's own values.
- Task values come from `AiTaskDef.effort` / `maxTokens` in `src/ai/tasks/*.ts`. The two draft streams use `DRAFT_EFFORT` 'high', `DRAFT_MAX_TOKENS` 16000 and `CONTINUE_EFFORT` 'low', `CONTINUE_MAX_TOKENS` 16000 (`src/ai/tasks/draft-chapter.ts`, called from `src/server/ai-features.ts`). Other caps: interview-question 2000, style-suggest 4000, draft-beats 4000, interview-extract 8000, draft-repair 8000, paragraph-trim 8000, scene-rewrite 8000, chapter-extract 16000, continuity-check 16000, direction-advice 16000, proofread 16000, reader-sim 16000.
- Product code does not read `maxTokensFloor` or `EvalClient` (grep: only `eval-client.ts` and `models.ts`). A cut-off is raised by the inner clients as `AppError` with `MAX_TOKENS_MESSAGE` (`src/ai/anthropic.ts`, also used by `src/ai/ollama.ts` for `done_reason: length` and by `src/ai/responses.ts`). `EvalClient.settle` stores it as `error.message` with `kind: 'model'`, and `usage` is the billed usage from `billedUsageOf`.
- `blindCallRecord` (`eval/novel/blind.ts`) deletes only `effortRequested`, `thinkRequested`, `maxTokens`, `productTimeoutMs`, `speed`; every other key passes through `maskDeep`.
- `RunSummarySchema` (`eval/novel/steps/finish.ts`) is a non-strict `z.object`; every block added after the first version is optional and "a block that was not measured is left out, never written as zeros".
- The novel-eval workflow (`.claude/workflows/novel-eval.js`, `runnerPrompt`) runs `init` without extra flags on every invocation; an existing run dir resumes. So a compare run must be created by hand first and resumed by the workflow, exactly as `--helper-think` runs are (F4).

Numbers from the saved runs `eval/results/novel/2026-10-18/run-0{1,4,5}-{ko,en}/calls/*.json` (178 calls; python3 over the JSON):

- Every call in a run has one `effortRequested` and one `maxTokens`: qwen `max`/32000 (62 calls), haiku and luna `high`/32000 (116 calls). The records cannot show the task values.

## Gating

- Option-only. `--product-limits` defaults to off; `config.json` has no `productLimits` key unless it was given as `true`; `EvalClient` reads it as `o.productLimits === true`. A run without it sends the same effort, maxTokens, model, system and prompt to the inner client as before (test "the default request is unchanged").
- Not provider-gated. The option applies to every profile because it only removes a floor that the eval added. It is meant for cloud (R2l: Haiku ko and en). Local use is allowed but documented as cloud-only for now (Risks).
- The cloud default path stays as the spec says: no change to effort (`high`), no change to maxTokens unless the option is on, no new inner-client behaviour. The only default-path change is three extra JSON fields in each call file and one optional `outputCap` block in `run-summary.json`.
- Nothing under `src/` changes, so product behaviour cannot change.
- Resume rule: a given flag must match the run; an absent flag resumes the run as created. The novel-eval skill therefore keeps working on a run created by hand.

## Risks

- R2l will cut things off, by design. The Haiku ko draft used 13,208 of 16,000 tokens (about 10,000 of them thinking) in the 2026-10-18 run, interview-question 1,740 of 2,000. A cut-off is a `kind: 'model'` failure: `withModelRetry` retries once, then records it in `failed`. For the interview, a failed `interview:ask` counts as an asked turn and the run goes on, so an R2l run can have fewer interview turns than R2b. This is measured data (`failed`, `retried`, `outputCap.cutOff`), not something to work around.
- R2l is not an exact product replay: the eval sends effort `high` to every call (27 of 29 calls differ from the task's own effort in the 2026-10-18 cloud runs). The higher effort burns more thinking tokens under the smaller cap than the product would. The spec keeps effort `high` (user decision); `taskEffort` in the records makes the gap visible. Say so in the R2l result document.
- Local profiles with `--product-limits`: qwen and gpt-oss went over the task caps in 2026-10-18 (examples in Evidence), and exaone has a 32,768-token context. The option is not refused, so a developer can still try it, but the README says cloud-only.
