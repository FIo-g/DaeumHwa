# P1. Beat scene count follows the draft length plan (app-local, eval only)

STATUS: ready. The spec row holds as written (the 1-6 cap in the beat prompt and the plan's `<scene_budget>` in the prose prompt disagree in code). Two facts the orchestrator should know: (1) no saved run contains a beat call, so the conflict is shown by code and arithmetic, not by outputs; (2) the cloud default path never calls `draft-beats`, so R2a and R2b cannot show an effect. The only round 2 measurement of P1 is R2t (`--two-step on`, which needs M5). One addition beyond the spec row is marked "Part B" and can be dropped without breaking Part A (see Open questions).

Branch `feat/ai-improvement-round2` (tip 3a05674). Find code by symbol name; line numbers are for this tip and move.

## Goal

When a two-step draft runs, the beat list (`draft-beats`) and the prose call (`draft-chapter`, then `draft-continue`) must talk about the same number of scenes.

Today they cannot:

- The beat call is told "1 to 6 scenes" and never sees the length plan.
- The prose call is told `<scene_budget>장면 N개, ...` from `draftLengthPlan(targetChars).sceneCount`, and also told by `BEATS_RULE` to follow the beat list exactly.

Fix, in two parts:

- Part A (the spec row): the beat call gets the plan's scene count as an exact target and loses the fixed 1-6 range.
- Part B (small guard, see Open questions): if the beat list still comes back with another length, the prose `<scene_budget>` uses the real list length, so the two numbers never disagree in the prose prompt.

## Design (TDD: write each test first, watch it fail, then implement)

### Part A. Tell the beat call the planned count

1. `src/ai/tasks/draft-beats.ts`, `DRAFT_BEATS_SYSTEM`. Replace the 1-6 rule line with these two lines (same position, between the intro/`규칙:` lines and the per-scene rule; every other line, including `TAG_DATA_RULE` second to last and `- 모든 출력은 한국어로 쓴다.` last, stays byte-identical):
   ```
   - 작가의 지시(<instructions>)에 있는 사건을 <scene_count>에 적힌 개수의 장면으로 나누고, 이야기 순서대로 놓는다. 장면 수를 늘리거나 줄이지 않는다.
   - 사건이 장면 수보다 적으면 긴 사건을 앞부분과 뒷부분으로 나누되 장소는 바꾸지 않는다. 사건이 장면 수보다 많으면 이어지는 사건을 한 장면으로 묶는다.
   ```
   The "do not change the place" clause keeps a split event from becoming an invented move that `BEATS_RULE` would then forbid in the prose.
2. Same file, `draftBeatsTask.buildPrompt`. Keep the shared sections from `buildDraftPrompt(..., { omitTargetLength: true })` and append the count as the LAST section:
   ```ts
   buildPrompt: (input) =>
     [
       buildDraftPrompt({ ...input, beats: null }, { omitTargetLength: true }),
       '',
       `<scene_count>${draftLengthPlan(input.targetChars).sceneCount}</scene_count>`,
     ].join('\n'),
   ```
   Import `draftLengthPlan` from `@/lib/draft-length`. The result ends with `</previous_tail>\n\n<scene_count>N</scene_count>`. The tag holds only a number (no Korean), so `scaffold.ts` needs no rule and the en prompt translation, tag-order test and `hangulLeft` stay clean. Update the header comment of the file: the scene count comes from `draftLengthPlan`, the same source the prose `<scene_budget>` uses.
3. `eval/novel/localize/en/draft-beats.ts`: replace the line "- Split the events in <instructions> into 1 to 6 scenes, in story order." with these two lines (all other lines unchanged):

   ```
   - Split the events in <instructions> into exactly the number of scenes given in <scene_count>, in story order. Do not add or drop scenes.
   - If there are fewer events than scenes, split a long event into an earlier and a later part and keep the place the same. If there are more events than scenes, put consecutive events into one scene.
   ```
   No Hangul. `EN_SYSTEMS['draft-beats']` already points at this constant, and the `en-systems.snapshot.json` fixture has no draft-beats key, so no fixture changes.

Existing test `src/ai/tasks/draft-beats.test.ts`, case "shares the draft prompt sections instead of copying them": it pins `draftBeatsTask.buildPrompt(sample)` `toBe(buildDraftPrompt(sample, { omitTargetLength: true }))`. ### Part B. The prose prompt follows the real list length

5. `src/lib/draft-length.ts`: `draftLengthPlan(target: number, sceneCount?: number)`. When `sceneCount` is an integer >= 1 it replaces the computed count (use `Number.isInteger(sceneCount) && sceneCount >= 1`); any other value, including `undefined`, keeps the current formula. `charsPerScene = Math.ceil(target / count)` uses the chosen count. `minChars` and `maxChars` do not change. `continuationPlan` still calls `draftLengthPlan(target)` with one argument (only `maxChars` is used there).
6. `src/ai/tasks/draft-chapter.ts`: add to `DraftPromptInput` `beatSceneCount?: number` with a JSDoc: "Scene count of `beats`. With a non-empty `beats` it replaces the plan's scene count in `<scene_budget>`; ignored without beats." In `buildDraftPrompt` change the single line `const length = draftLengthPlan(input.targetChars)` to `const length = draftLengthPlan(input.targetChars, input.beats ? input.beatSceneCount : undefined)`. Nothing else in that function changes. With `beats` absent/null/'' the output is byte-identical to today (`PLAIN`, `CONTINUATION`, `WITH_VOICES`, the speech-off pins).
7. `src/server/ai-features.ts`, `startDraft`: where `finalInput` is built from `beatsRun`, add `beatSceneCount: beatsRun.output.scenes.length` next to `beats: renderBeats(beatsRun.output)`. The empty-list guard just above guarantees the value is at least 1. `finalInput` is what `completeDraft` passes to `buildContinuationPrompt`, so the continuation uses the same count. Do not touch `promptInput` (the beat call must not receive `beatSceneCount`).
8. Run the commands under Definition of done. No docs change is needed (the eval README does not describe the beat prompt). The older design doc `docs/superpowers/specs/2026-10-19-ai-improvement-design.md` still says "1-6 scenes"; leave it as history.

## Gating (how the cloud default stays as the spec says)

- `draft-beats` runs only through `startDraft(..., { twoStep: true })`. Product code never passes `twoStep`; the eval passes it for local profiles (`isLocalProfile`) and, after M5, for any profile when `--two-step on` is set. So the cloud default path makes no beat call and no behaviour of it changes.
- Part B only reads `beatSceneCount` when `beats` is non-empty, and only `startDraft` sets it, only from a real beat run. Without beats, `buildDraftPrompt` and `buildContinuationPrompt` produce the same bytes as before: this is pinned by `PLAIN`, `CONTINUATION`, `WITH_VOICES` in `draft-chapter.D.test.ts` and the `speech-off.test.ts` strings, and by the new "ignores `beatSceneCount` without beats" test.
- `DRAFT_SYSTEM` is not touched, so P4/P5 can edit it later without a conflict from this track.
- No new option, flag or env var is needed.

## Risks

- Not measurable in the default round 2 runs. R2a/R2b are cloud with the one-step draft, and no local run is planned this round. The first measurement is R2t (`--two-step on`, M5), which should read `chapters/01.attempt-1.beats.json` (scene count against `draftLengthPlan(targetChars).sceneCount`) and the prose `<scene_budget>` in the draft call record. State this in the result document; do not claim a P1 effect from R2b.
- Count above the number of events (en fixture: 8 scenes for 6 events) makes the model split events. The system tells it to keep the place; if R2t shows invented moves, the fallback is "about N" wording, not the old cap.
- Models may ignore the count. Part B makes that harmless for the prose prompt, but the length per scene (`charsPerScene`) then differs from the 1500-char scene target. Accepted.
- `draft-beats` `maxTokens` stays 4000. A 13-scene list (target 20000) after P2 adds fields per scene could be cut and fail the format check. P9 widens the budget on a local retry; cloud keeps the product limit. Not changed here.
- A forged opening `<scene_count>` typed in the author's instructions is not neutralized (`neutralizeTags` only breaks closing tags). The real tag is last, after every author text; accepted.
- Merge order inside the one working tree: P1 first, then P2 (same files: `draft-beats.ts` system and `buildPrompt`, `draft-beats.r2.test.ts`). P2 must add its own system lines around the two lines from step 1 and must keep the `<scene_count>` section last in `buildPrompt`.

## Open questions (default chosen)

1. Include Part B? Default: yes. The spec row only names the beat side, but without Part B a miscounted list reproduces the exact conflict in the prose prompt. It is about 6 changed lines plus tests and is separable: dropping steps 5-7 and the Part B tests leaves Part A complete.
2. Exact count or a range? Default: exactly N in the prompt, no schema bound, no service-side rejection or retry on a mismatch. A mismatch costs a whole local call to retry and Part B already neutralizes it.
3. A cap for the scene count (the old 6)? Default: none. The app's own target limits bound the plan to 2-13.
4. Where in the beat prompt does the count go? Default: as the last section, so it is the last thing the model reads before answering. The prose prompt keeps its length lines at the top; the two prompts differ in layout on purpose.
5. Why change the existing `draft-beats.test.ts` case instead of keeping it green? Putting the count inside `buildDraftPrompt`'s `omitTargetLength` branch would keep it green but break the pinned "removes only the two length lines" test in `draft-chapter.D.test.ts` and touch the draft builder P4/P5 edit. The one-line update in `draft-beats.test.ts` is the smaller change.
