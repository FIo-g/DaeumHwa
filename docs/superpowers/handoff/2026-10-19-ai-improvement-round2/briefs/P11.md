## Goal

An interview answer whose topic is the core topic `문체` (or `style`) must become exactly one `style_card` proposal and nothing else: no `entry_create`, `fact_create`, `thread_create` or `relation_create`. The author can edit the card in the proposal editor and approves it as usual. Nothing is written to the wiki tables by the interview; approval goes through the existing `approveProposal` path (change log included).

## Gating

- No flag and no profile gate. The spec lists P11 as `app`: cloud and local interviews both take the new path, and it runs only when the canonical topic is `문체`.
- The cloud default path changes only for those turns. Every other turn calls `interview-extract` with the same system and prompt text as before. No system prompt, schema, task def or `AI_TASKS` entry changes, so the "speech off is byte-identical" pins and the EN snapshot stay as they are.
- `AI_SPEECH_STYLE` is not involved. With the speech feature on, a character's voice is asked under `주요 인물`, not `문체`, and takes the old path.

## Risks

- **R2b comparability.** In a run where the question model asks the style topic (all four cloud runs did) and the author agent approves the card, the work gets a second work-level style card next to the seeded `작품 문체` / `Work style` card, and `startDraft` prints both in the draft prompt. P4 and P5 change the same draft prompt, so an R2b change in Q1 to Q8 cannot be split from this. Accepted (the spec measures the P set together). Say so in the results doc and record, from `author-decisions.jsonl`, whether the style proposal was approved or rejected as a duplicate. The author context does not list style cards, so either outcome is plausible.
- **Silent drop was rejected.** Skipping the proposal when a work-level card already exists would remove the contamination but would throw away the author's answer without a trace. Not done.
- **The tone/rules split is a convention.** The first sentence is not always the tone. The text is complete and editable before approval, which is why a split without AI is acceptable.
- **Topic detection depends on the question model's `topic` text.** `시점` or `톤` alone would not match and would still leak. Not seen in the saved runs (4 of 4 were `문체`, `style` or `Style`). Widening `CORE_TOPICS` is out of scope because the planner shares it.
- **`canonicalTopic` resolves in core order.** A topic that names an earlier core topic as well (`주인공의 문체`) resolves to the earlier one and takes the old path. Accepted.
- **Fewer AI calls in the run summary.** A run that asks the style topic shows 11 `interview-extract` calls instead of 12. Say so when comparing R2a and R2b tables.
- **No dedupe for a repeated style answer.** Two interviews that both ask the style topic can leave two pending style cards. The question prompt already lists covered topics.
- **Long answers.** No cap on `tone` and `rules`; the author can edit. A pasted prose sample would become bullet lines.

## Open questions (default chosen)

- AI-written card or deterministic mapping? Default: deterministic. A new task name needs `AI_TASKS`, `EN_SYSTEMS`, `en-systems.ts`, fake outputs, the sample placeholder, the EN snapshot and a `TASK_DEFS` entry in the eval client, and it would collide with other P tracks. The mapping loses nothing and adds no call.
- First sentence as `tone`, or the whole answer as `rules`? Default: first sentence as `tone`, the rest as bullet `rules`, matching the seeded card's shape and giving the proposal list a visible detail line.
- Proposal `source`: `interview` or `style`? Default: `interview`, so `listProposals({ source: 'interview', sourceRef: turnId })` (used by `AnswerProposals` flow and the eval interview step) returns it with the turn.
- Propose when a work-level card already exists? Default: yes (see Risks).
- Should the style answer also be extracted for other facts? Default: no, the spec says "문체 카드 제안으로만".
