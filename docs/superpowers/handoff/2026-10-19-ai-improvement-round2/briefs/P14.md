# P14. Proofread: drop `awkward` suggestions on the server and prefer whole-word quote hits (APP, cloud and local)

STATUS: changed. The `awkward` filter is built as the spec says. The word-boundary half is already partly in the code: commit 2cff60a made `expandQuote` (`src/server/chapter-check.ts`) refuse to grow a quote into a longer word, and the test 'does not expand a quote into a longer word' in `chapter-check.J.test.ts` pins it. One gap is left, and P14 shrinks to it: when a quote has hits that are whole words AND hits inside a longer word, the FIRST hit decides which kind of hit is used, so `할수` in `할수록 좋다. 그도 할수 있다.` maps into `할수록` and skips the real `할수 있다`. The saved runs contain no case of that gap (all 30 saved suggestions are either the only hit of their quote or a clean pair), so the boundary half is hardening found by reading code, not a measured fix. Say so in the results doc.

Written against `feat/ai-improvement-round2` at 3a05674. Find code by symbol name; line numbers move. P14 runs after P3 in the same worktree (P3 also edits `src/server/chapter-check.ts`, another function). See Dependencies.

## Goal

1. A proofread suggestion of kind `awkward` never reaches the author. The model may still answer it (the schema keeps the kind, so a model that uses it does not fail the call); the server drops it before anything else looks at it.
2. When the app picks where a model quote applies, whole-word hits win over hits inside a longer word. If no hit is a whole word, behaviour stays as it is today (nothing is dropped).

Prompts are NOT changed (see Open questions 1). The wire shape (`ProofreadSuggestion`, route JSON, panel `ProofreadItem`) is not changed.

```ts
/** Whether `ch` is a letter or a digit in any script (Hangul, Latin, ...). */
export function isWordChar(ch: string | undefined): boolean {
  return ch !== undefined && /[\p{L}\p{N}]/u.test(ch)
}

/**
 * Whether a non-empty range of `text` cuts no word at either edge. An edge cuts a word only when
 * the character inside the range and the one outside are both letters or digits: `할수` inside
 * `할수록` is cut at the end, `갔다.` before `그` is not (`.` is not a word character). Korean
 * attaches particles and endings without a space, so a Hangul syllable next to a hit means the hit
 * sits inside a longer eojeol.
 */
export function isWholeWordRange(text: string, range: { start: number; end: number }): boolean {
  const cutsStart = isWordChar(text[range.start - 1]) && isWordChar(text[range.start])
  const cutsEnd = isWordChar(text[range.end - 1]) && isWordChar(text[range.end])
  return !cutsStart && !cutsEnd
}
```

   (`text[-1]` is `undefined`, which is a non-word character, so the text edges count as boundaries.)

## Gating

None. This is an app change on purpose (spec row P14, scope `app`): the filter and the word rule run for every provider, cloud and local, with no flag and no option. The M5 options (`--speech`, `--two-step`) and `--product-limits` have no effect on it. ## Risks

- Valid catches labelled `awkward` are lost (2 of 21 in the saved runs, 1 of 9 on cloud). Accepted by the spec. The prompt asks for `awkward` only on ungrammatical sentences, so a truly ungrammatical sentence can vanish. See Open questions 1.
- The model can relabel taste items as `spelling` or `grammar` and pass the filter (gpt-oss already did it once: `종과 봉인 사이 규칙` grammar, rejected). The filter only cuts the label. Read the R2b author decisions before claiming the acceptance ratio is fixed.
- The proofread metric reads 0 `awkward` from now on: `proofreadStats.awkward` and the summary field of the same name (`eval/novel/steps/finish.ts`) count the FINAL list. Do not read 0 as "the model stopped". Use the raw call records (below).
- The acceptance ratio can rise because the denominator shrank, not because suggestions got better. Report `quoteAcceptanceRatio` and the raw and final counts together.
- Preferring whole-word hits can move a suggestion away from the place the model meant (it saw a stem inside a longer word and meant that one). The fallback keeps today's behaviour when no hit is a whole word. One case: a model that quotes a stem on purpose (`4층이상` inside `4층이상은`) still works, because no hit is a whole word.
- The panel's `replaceQuoteText` falls back to `indexOf` (first substring) when the text moved and `item.start` no longer matches. That path can still hit a longer word. Out of scope (the panel is read-only for this track).
- Editing the existing fixtures is the only change to existing tests; it is a one-word swap and does not change what they test (J's overlap test now exercises the overlap guard again).
- `chapter-check.ts` is edited by P3 too. The regions are disjoint (`runChapterCheck` versus `expandQuote` and the import block). Re-read the file before editing; keep P3's imports.

## Open questions (default chosen)

1. Change the prompt so ungrammatical sentences use `grammar`, and tell the model `awkward` is gone? Default: NO. Reasons: the spec asks only for a server filter; leaving `awkward` available gives the model a bin for taste edits that the server then drops (removing the bin would push those into `spelling` or `grammar`, which the filter cannot see); the cloud prompt, its English twin and the snapshot stay byte-identical, so R2b attributes any change to the filter. If R2b shows valid ungrammatical sentences lost, a follow-up can rewrite the kind line in ko and en and update `en-systems.snapshot.json` in the same commit.
2. Filter in `postProcess` or in the service? Default: `postProcess` (before `keptQuotes`, per part, pure test, one place for both providers). Cost: the stored `ai_runs.output` no longer shows the dropped items; the eval's raw call records still do.
3. Drop a quote that only occurs inside longer words? Default: no, keep the old rule (spacing fixes such as `4층이상` in `4층이상은` are valid).
4. Remove `awkward` from `PROOFREAD_KINDS`? Default: no (a stale stored run or a model that still answers it must not fail schema parsing; J decided the same).
5. Apply the whole-word preference to one-character quotes and to whitespace-collapsed matches? Default: no. They keep mapping to the first hit (pinned by the J test). Such quotes are rare and ambiguous.
6. Store the count of dropped items in the product? Default: no. The harness reads it from the raw call records (script below).
