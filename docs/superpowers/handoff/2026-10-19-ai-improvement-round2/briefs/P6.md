## Goal

After a draft is finished, the author can press "다듬기" in the AI 초안 panel. The server runs the two existing round-1 passes in the same order the eval uses: E1 (`trimOverlongParagraphs`, paragraphs over 3 sentences) and then E2 (flags from `findDraftFlags`, rewritten by `draftRepairTask`, applied with `applyDraftEdits`). The panel shows the result as a marked preview (removed text struck, new text highlighted). The author applies it or discards it. Nothing changes before the author presses "적용". Applying updates the draft in the panel and the stored draft text of the run, so "현재 원고 끝에 붙이기" and "새 회차로 만들기" both use the refined text.

This is product code only. The eval harness, `startDraft`, the `/draft` route, `repairDraft`, `trimOverlongParagraphs` and both task definitions stay byte-for-byte as they are, so R2a/R2b/R2s/R2t/R2l numbers are not affected (P6 is not a measured track; it has no eval hook).

## Evidence (verified in code or saved runs)

- No UI calls the passes. `trimOverlongParagraphs` (src/server/draft-paragraphs.ts) has one non-test caller: `trimStage` in eval/novel/steps/chapter.ts. `repairDraftAction` (src/server/actions/ai-features.ts) is imported by no component (grep `repairDraftAction` in src: only its definition). E1 and E2 briefs both said "no UI in this track" and left this for a later track.
- `repairDraft` cannot give a preview. It ends with `replaceRunOutput(db, runId, { ...output, text: repaired.text, originalText, repair })` and is idempotent through `output.repair` (a second call returns the stored result and makes no AI call). Using it for a preview would change the stored draft before the author decides. The eval depends on exactly this behaviour, so do NOT edit it.
- A draft the panel shows is `ai_runs.output.text` of a `draft-chapter` run (`startAiStream` stores `{ text }`; `completeDraft` replaces it with the joined text; streamed text equals stored text). `createChapterFromDraft` builds a chapter from that stored text. `CreateChapterFromDraftSchema` (action) has no `body` field on purpose (E1 brief: a client-supplied body would bypass the run's recorded text and its `ai_draft` provenance). So a refined text that only lives in panel state would be lost on "새 회차로 만들기". The apply step must update the stored text, and the server must be the one that produces the refined text. Hence a server-held candidate.
- Panel shape today (src/components/writing/panels/draft-panel.tsx, `DraftPanel`): state `draft`, `runId` (from header `X-Run-Id`), `complete`, `stopped`, `appended`; `finished = !streaming && draft !== null && draft.length > 0`; buttons "현재 원고 끝에 붙이기" (`api.appendText`) and, only when `complete && runId`, "새 회차로 만들기". A stopped or errored draft has no done run row (`createChapterFromDraft` and `repairDraft` both require `run.status === 'done'`).
- The proofread flow to follow (src/components/writing/panels/proofread-panel.tsx): `useAiRun` + `AiRunStatus` (cancel), `postAction` to a route handler (`/api/works/{workId}/chapters/{chapterId}/proofread`, `maxDuration = 300`, because Next runs Server Actions one at a time), `runAction` for toasts, editor gate `canEditChapter` / `EDITOR_ONLY_NOTE`, nothing changes until the author clicks, a stale text is reported ("원고가 바뀌어 ... 다시 검사해 주세요."), `offerUndo` after an edit. Work-level route helper: `runWorkRoute` in src/app/api/works/[workId]/work-route.ts (used by the advice route).
- Time limits: `paragraphTrimTask` has no `timeoutMs` (default `DEFAULT_AI_TIMEOUT_MS` 120,000), `MAX_TRIM_ROUNDS = 2` (up to 240 s); `draftRepairTask.timeoutMs = 180_000`. Worst case 420 s is more than a route's 300 s. `AiRunMeta.timeoutMs` beats `task.timeoutMs` in `runAiTask`, so the repair call can be given the time that is left. `startDraft` uses the same idea (`DRAFT_TOTAL_BUDGET_MS`, `MIN_CONTINUATION_MS`).
- Existing diff helper, client and server safe: `diffTexts(a, b, 'words')` and `DiffPart` in src/lib/diff.ts (whitespace-delimited eojeol, lossless join). `VersionDiff` in src/components/writing/version-diff.tsx renders `ins`/`del` parts (its `DiffBody` is not exported; copy the class names).
- How much work there is for the passes on saved cloud ko drafts (eval/results/novel/2026-10-18, `chapters/01.md`; run-04-ko is haiku-5.5, run-05-ko is luna-6): paragraphs with more than 3 sentences, counted with a Python port of `splitSentences`/`countSentences` (approximate; the TS functions were not run): haiku ko 5 of 86 paragraphs, luna ko 0 of 106. These drafts predate E1/E2, so they have no trim or repair records, and the repeated-word and sample-copy rates need the TS code (M7 and R2b report them). Conclusion: E1 has real work on some cloud drafts; the button must handle "nothing to fix" as a normal outcome.
- Product only builds Anthropic or Opencode clients (src/ai/index.ts `getAiClient`); `OllamaAiClient` is built only in eval/novel/models.ts. No local-provider case exists in the product.

## Design (TDD, in this order)

0. Decisions the spec leaves open (chosen to match its text and the rules in CLAUDE.md):
   - The draft is not in the manuscript until the author appends it, so "apply" replaces the draft (panel state and the run's stored text), not the editor text. The manuscript is never touched by P6; `api.replaceQuote` and `offerUndo` are not used.
   - Apply is all-or-nothing (apply or discard the whole preview). Per-sentence apply would need a client-composed text stored on the run. A 되돌리기 toast is not built; the pre-refine text stays in the run output as `originalText`.
   - One button runs E1 then E2 on the text E1 returned (same order as the eval's `trimStage` then `repairBestEffort`). The foreign-script repair (C) is eval and local only and is not included.
   - The 3-sentence limit is the constant `PARAGRAPH_MAX_SENTENCES` (E1 decision); style cards are not read for it. `lang` is not passed (product is Korean).

1. `src/lib/draft-refine.ts` (tests first, `src/lib/draft-refine.r2.test.ts`). Pure, no server imports (it is imported by a client component). ## Interface

```ts
// src/lib/draft-refine.ts  (client-safe)
import type { DiffPart } from '@/lib/diff'
export type RefineRepairState = 'none' | 'done' | 'skipped' | 'failed'
export type DraftRefinePreview = {
  runId: string
  changed: boolean
  parts: DiffPart[] // [] when !changed; join of equal+delete is the stored draft, equal+insert the refined text
  paragraphsBefore: number // paragraphs over 3 sentences before E1
  paragraphsAfter: number // after E1 (unfixable dialogue paragraphs stay)
  flagged: number // flags found on the trimmed text
  repaired: number // edits applied by E2
  repairState: RefineRepairState
  beforeChars: number // draftCharCount
  afterChars: number
}
export type AppliedRefinement = { runId: string; text: string }
export function refineSummary(p: DraftRefinePreview): string
export function refineRepairNote(p: DraftRefinePreview): string | null

// src/server/draft-refine.ts
export const REFINE_BUDGET_MS = 280_000
export const MIN_REPAIR_MS = 20_000
export async function previewDraftRefinement(
  db: Db, actor: Actor, input: { workId: string; runId: string },
  client?: AiClient, signal?: AbortSignal, now?: () => number,
): Promise<DraftRefinePreview>
export async function applyDraftRefinement(
  db: Db, actor: Actor, input: { workId: string; runId: string },
): Promise<AppliedRefinement>

// src/server/actions/ai-features.ts (added)
export async function applyDraftRefinementAction(input: unknown): Promise<ActionResult<AppliedRefinement>>

// stored on the draft-chapter run, key `refinement` (removed on apply):
// { base: string; text: string; paragraphs: number; sentences: number }
// after apply the run output also has: originalText (first original, kept), refined: { paragraphs, sentences }
```

## Gating

- Cloud default path: unchanged. Nothing runs until the author presses 다듬기: `startDraft`, the `/draft` route and the stream are untouched, so a draft costs exactly what it did. No env flag, no setting, no `isLocalProvider` or `queue === 'local'` check: the product has no local provider (see Evidence). The two stages run one after another, so they would also respect a one-call-at-a-time provider.
- Eval: no file under `eval/` imports `src/server/draft-refine.ts`, `src/lib/draft-refine.ts` or the new action. After the work, `grep -rn "draft-refine\|applyDraftRefinement" eval` returns nothing. This is why R2b and the compare runs stay comparable with R2a.
- Access: `previewDraftRefinement` and `applyDraftRefinement` check `requireWorkRole(..., 'editor')` first; non-members get `NOT_FOUND`, viewers and commenters `FORBIDDEN`; the run must belong to the actor, the work and `task === 'draft-chapter'`. The panel already hides all controls from non-editors and archived chapters (`canEditChapter`).
- Rules from CLAUDE.md: the AI never writes wiki tables (only `ai_runs.output` changes, so no `change_log`); services throw `AppError(code, koreanMessage)`; the action never throws; copy is Korean, identifiers and comments English.

## Risks

- Latency: up to three sequential calls (trim rounds at effort low, one repair at effort medium); typical cloud time is tens of seconds. `maxDuration = 300`, `REFINE_BUDGET_MS = 280_000`, the repair gets `min(180 s, time left)` and is skipped under 20 s left. Worst case the trim alone takes 240 s and the repair is skipped; the preview then says so.
- Stored size: the candidate holds `base` and `text` (each up to the draft length, 20,000 characters at most by `TARGET_MAX`), and `exports.ts` writes done `draft-chapter` run outputs into the backup as raw JSON. Accepted, as the E2 brief did for `originalText`. A candidate the author discards stays until the next preview or apply.
- Staleness: apply refuses when `output.text` no longer equals `base`. Nothing else writes a done draft's `text` in the product (only `repairDraftAction`, which no UI calls).
- Word diff: `diffTexts(..., 'words')` marks changed eojeol, finer than "changed sentences"; a split paragraph shows as an inserted blank line. Good enough for a review; no extra summary per sentence.
- Unfixable dialogue paragraphs: `isValidTrim` rejects any trim that cannot keep a quoted span, so `paragraphsAfter` can stay above 0; `refineSummary` says so instead of claiming success.
- A new draft started while a refine request is in flight unmounts `DraftRefine`; `useAiRun`'s unmount effect aborts the request silently. The server run stops through `request.signal`.
- The 6 lines that collect `examples` and `exempt` repeat `repairDraft`'s. If a later round changes how flags are collected, both places must change (comment says so).
- Old test `draft-panel.test.tsx`: see step 6 for the one conditional edit.

## Open questions (defaults chosen)

- Per-change apply or all-or-nothing? Default all-or-nothing (stored text must equal the shown draft).
- A 되돌리기 after apply? Default no; the original stays in `originalText` for a later track (a `revertDraftRefinement` service would be about 20 lines).
- Does discard clear the stored candidate? Default no (client-only); apply checks `base`.
- One button or two (문단 다듬기, 반복어·견본 수리)? Default one, fixed order E1 then E2 (spec: "다듬기" button).
- Should the 3-sentence limit follow a style card? Default constant 3 for all works (E1 decision).
- Share the flag collection with `repairDraft` by extracting a helper? Default no (keeps `ai-features.ts` free for P7/P10/P15 edits); revisit after the P block is merged.
- Word-level or sentence-level diff? Default word-level via the existing `diffTexts`.
- Foreign-script repair and English drafts? Not included (local/eval only, product is Korean).
