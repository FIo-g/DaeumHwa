# M1. Power and energy mode in the local-run records, and a low-power warning on the status line (harness)

STATUS: ready. The track can be done as the spec says. Two things the spec does not spell out are decided here and are part of the work: (1) the reviewer's blinded copy must drop the new `power` data, or it would tell the blind reviewer that a run is local; (2) the worker's own output must never carry the warning, because `worker.log` is copied into the blinded copy. One fact differs from the spec's section 7: the live Mac now reports `powermode 2` on both power sources, not `powermode 1` on AC (see Evidence). That does not change the work. The record is how a later session proves which mode a local run had.

Round 2, branch `feat/ai-improvement-round2` (tip 3a05674). Wave: M (harness), first of the M order. Find code by name; line numbers are not given because they move.

## Goal

For local (Ollama) runs only:

1. Record the machine's power source and energy mode on every call record (`calls/NNN-<task>.json`) and as one aggregate block in `run-summary.json`.
2. Put a `warning` on the `status` and `advance` JSON line when the Mac is in Low Power energy mode now, or when any recorded call of the run started in it.

Cloud and fake profiles, the product code in `src/`, and the 2026-10-18 saved runs are not changed. The track adds no package, no setting and no change to how a run is scheduled or paused. A warning never stops a run.

## Evidence (verified 2026-10-19 on this Mac, read-only)

- The records have no power data today. `CallRecord` in `eval/novel/eval-client.ts` has no power field, and the saved calls of `eval/results/novel/2026-10-18/run-01-ko` (32 calls) and `run-01-en` (30 calls) have none either. So whether the saved qwen speeds were measured in Low Power cannot be checked afterwards. Per-call output speed in those runs is not steady: qwen ko 22.4 to 35.5 tokens/s (median 30.8), qwen en 13.6 to 35.9 (median 29.5). The gpt-oss ko run in progress (`2026-10-18/run-02-ko`, 26 calls so far) ranges 25.1 to 61.4 (median 44.8). Something explains that spread. M1 only makes one candidate cause visible.
- `pmset` is at `/usr/bin/pmset`, arm64, macOS. `pmset -g batt` prints a first line such as `Now drawing from 'AC Power'` (other values: `'Battery Power'`, `'UPS Power'`). `pmset -g` prints a `Currently in use:` block that holds the active energy mode as a `powermode <n>` line. A Mac laptop can also print a `lowpowermode <0|1>` line. The man page of `pmset` on this Mac documents neither key, so the mapping below rests on the spec (section 7: AC `powermode 1` is Low Power) and on the common reading 0 automatic, 2 high. Treat 1 as certain, the others as likely. The table is one constant, so it is a one-line fix if a toggle test shows otherwise.
- Today `pmset -g` prints `powermode 2` in the `Currently in use:` block, and `pmset -g custom` prints `powermode 2` for both `Battery Power:` and `AC Power:`. The spec's section 7 says AC was `powermode 1`. So the live state is not Low Power now; the user probably changed it. The warning exists so this can never be silent again.
- Cost: `pmset -g` plus `pmset -g batt` took 18 ms together (measured with `time`). A local call takes seconds to tens of minutes, so one read per call start is negligible. Sampling is synchronous (`execFileSync`), which is fine because a local call is the only AI call running and nothing else needs the event loop in that moment.
- Blinding precedent: `blindCallRecord` in `eval/novel/blind.ts` deletes the profile fingerprints (`effortRequested`, `thinkRequested`, `maxTokens`, `productTimeoutMs`, `speed`) and the type `BlindedCall` omits them; `blindRunSummary` deletes `speed`. F4 added `thinkRequested` there for the same reason. `power` exists only on local runs, so it is a fingerprint and must be handled the same way.
- `worker.log` is on the blind copy's allow-list (`writeBlindCopy` in `blind.ts`, masked but copied). The detached worker prints the JSON line from `runWorker` into it. So a warning computed inside `runWorker` would reach the reviewer.
- The workflow's runner agent returns the last `advance` JSON line verbatim as `detail` (`runnerPrompt` in `.claude/workflows/novel-eval.js`), and `pendingKeyOf(detail)` only reads `step` and `pendingKind`. An extra `warning` key on the line is therefore safe and reaches the orchestrator without any change to the workflow.
- `ModelProfile.queue` is `'local'` for qwen, qwen-t06, gpt-oss and exaone, `'cloud'` for Haiku and Luna, `'test'` for fake (`eval/novel/models.ts`). `EvalClient` already branches on `this.profile.queue === 'local'` for the lane (F4).
- The existing tests build `EvalClient` and `openRun` with the qwen profile in many files (`run.D.test.ts`, `run.C.test.ts`, `run.review.test.ts`, `eval-client*.test.ts`). They must not start calling the real `pmset`. So the reader is injected, never defaulted inside `EvalClient` or `openRun`.

## Design (TDD, in this order; each step ends with its tests green and `pnpm exec tsc --noEmit` clean)

1. **`eval/novel/power.ts`, pure parsers.** New file, no imports from other `eval/novel` files (it is imported by `eval-client.ts`, `finish.ts`, `blind.ts`, `cli.ts`; keep it cycle-free). Strict index access is on, so use `match?.[1]`.
   - Types `PowerSource`, `EnergyMode`, `PowerInfo`, `PowerReader`, constant `UNKNOWN_POWER` (always spread it: `{ ...UNKNOWN_POWER }`).
   - `parsePowerSource(batt)`: find `/Now drawing from '([^']+)'/`. `AC Power` gives `'ac'`, `Battery Power` gives `'battery'`, `UPS Power` gives `'ups'`, anything else or no match gives `'unknown'`.
   - `parseEnergyMode(text)`: if the text contains the line `Currently in use:`, look only at the text after it; otherwise at the whole text. Match lines `/^\s*(lowpowermode|powermode)\s+(\d+)\b/gm`. Rules, in this order: a `lowpowermode 1` line gives `{ mode: 'low', modeRaw: 'lowpowermode 1' }`. Else a `powermode <n>` line gives the mode from the constant table `POWERMODE_MODES = { 0: 'automatic', 1: 'low', 2: 'high' }` (any other number gives `'unknown'`) and `modeRaw: 'powermode <n>'`. Else a `lowpowermode 0` line gives `{ mode: 'automatic', modeRaw: 'lowpowermode 0' }`. Else `{ mode: 'unknown', modeRaw: null }`. `modeRaw` has single spaces (the pmset columns are collapsed).
2. **`readPowerInfo`.** `PmsetRunner = (args: string[]) => string`. The default runner is `execFileSync('/usr/bin/pmset', args, { encoding: 'utf8', timeout: 3000, stdio: ['ignore', 'pipe', 'ignore'] })` (absolute path, no PATH lookup). `readPowerInfo(deps = {})` with `deps.run` and `deps.platform` (default `process.platform`): off darwin returns `{ ...UNKNOWN_POWER }` and never calls the runner. Otherwise two separate `try/catch` reads, `run(['-g', 'batt'])` for the source and `run(['-g'])` for the mode, so one failing command keeps the other's value. It never throws.
3. **`powerSummary` and `lowPowerWarning`.**
   - `powerSummary(samples)` returns `null` for an empty list, else `{ sampled, lowPower, onBattery, byMode, bySource }`. `lowPower` counts `mode === 'low'`, `onBattery` counts `source === 'battery'`, the two maps count only observed values (no zero entries).
   - `lowPowerWarning({ live, samples })`: let `lowCalls` be the number of samples with `mode === 'low'` and `liveLow` be `live?.mode === 'low'`. Return `null` when both are false (a mode of `unknown` never warns). Otherwise return one string: the parts joined by a space + ` Local speed and time numbers are not comparable until the Energy Mode is Automatic or High Power.` Parts: `The Mac is in Low Power energy mode now.` when `liveLow`; `<lowCalls> of <samples.length> recorded local calls started in Low Power energy mode.` when `lowCalls > 0`. English, because this is an eval CLI operator message (the F4 precedent: eval CLI strings such as `unknown model:` stay English).
4. **Per-call record in `eval-client.ts`.**
   - `CallRecord.power?: PowerInfo` (doc: machine power state when the call started; local profiles only; absent on cloud runs and on records written before M1). `EvalClientOptions.readPower?: PowerReader`. `Prepared.power?: PowerInfo`.
   - Constructor: `this.readPower = o.profile.queue === 'local' ? o.readPower : undefined`. This is the single gate. A cloud or fake profile never reads power even if a reader is passed.
   - New private `samplePower(): PowerInfo | undefined`: undefined without a reader; otherwise `this.readPower()` inside `try/catch`, and on a throw `{ ...UNKNOWN_POWER }`. A broken reader never fails an AI call.
   - In `prepare()` call `samplePower()` as the FIRST statement, before `const startedMs = this.now()`. Then the 18 ms read is not part of `durationMs` (it shows up in `queueMs` of that call, which is honest: the call was not running yet). Put the result in the returned `Prepared`. `prepare` runs after the lane is taken (F4), so the sample is the state when the call really starts, not when it was requested.
   - `settle()`: add `...(call.power ? { power: call.power } : {})` to the record, after `thinkRequested`. Nothing else in the record changes. Streams and the abort-while-queued failed record go through `prepare` too, so they get the same field.
5. **Pass-through in `run.ts`.** `openRun(dir, o)` accepts `readPower?: PowerReader` and passes it to `new EvalClient({ ..., readPower: o.readPower })`. No default here (see Evidence, last bullet).
6. **Run summary block in `finish.ts`.** Add `PowerBlockSchema = z.object({ sampled: CountSchema, lowPower: CountSchema, onBattery: CountSchema, byMode: z.record(z.string(), CountSchema), bySource: z.record(z.string(), CountSchema) })` and `power: PowerBlockSchema.optional()` in `RunSummarySchema`. In `buildRunSummary`, after the `timeouts` line: `const power = powerSummary(calls.flatMap((c) => (c.power ? [c.power] : [])))` and `if (power) summary.power = power`. A run with no sample has no block (the file's rule: a block that was not measured is left out). Assigning `PowerSummary` to the zod-inferred type makes `tsc` catch drift between `power.ts` and the schema. `resummarizeRun` rebuilds the block from `calls/` for free.
7. **Blinding in `blind.ts`.** Add `'power'` to the `Omit` list of `BlindedCall`, `delete masked.power` in `blindCallRecord`, and `delete masked.power` in `blindRunSummary`. Update the doc comment above `blindCallRecord` ("profile fingerprints") to name power.
8. **Status line in `cli.ts`.**
   - `StatusJson` gains `warning?: string`. `formatStatus(state, pendingKind = null, warning: string | null = null)` adds `warning` only when it is a non-empty string, so the existing exact-shape test of `formatStatus` (cli.test.ts, `toEqual` with four keys) stays green.
   - New private `powerWarningFor(dir, state, readPower)`: load the config in `try/catch` (a dir without `config.json` gives `null`); take `MODEL_PROFILES[config.modelId]`; return `null` unless `profile?.queue === 'local'` (checked BEFORE calling the reader, so fake and cloud runs never read power). Read the samples with `readCallRecords(dir)` in `try/catch` (a corrupt file gives no samples), keep `c.power`. The live value is `state.status === 'done' ? null : readPower()` (a finished run says nothing about the machine now). Return `lowPowerWarning({ live, samples })`.
   - `summarize(dir, state = loadState(dir), readPower?: PowerReader)`: compute the warning only when `readPower` is given, and pass it to `formatStatus`.
   - `advanceRun`: `AdvanceOptions.readPower?: PowerReader`; `const readPower = o.readPower ?? readPowerInfo`; pass it at all three places that build the result: the `live` branch `summarize(dir, state)`, the non-new/running `summarize(dir, state)`, and `pausedError(dir, state, message, readPower)` (add the fourth parameter and pass it to its `summarize`). The warning is returned, never saved: do not put it in `state.message` or in any file.
   - `runStatus(o)`: `readPower?: PowerReader` in `o`, default `readPowerInfo`, passed to every `summarize` it calls.
   - `runWorker(dir, o)`: `o.readPower?: PowerReader`; `openRun(dir, { autoAuthor: o.fakeAuthor, readPower: o.readPower ?? readPowerInfo })`. Its own `summarize(dir, state)` call stays WITHOUT a reader, so the worker's JSON line (and `worker.log`) never carries a warning. Do not change `dispatch`: the defaults make the real reader the CLI behaviour, and `SpawnWorker` keeps its type.
9. **README (Korean).** See "README text" below.

export type PowerSource = 'ac' | 'battery' | 'ups' | 'unknown'

export const UNKNOWN_POWER: Readonly<PowerInfo>
export function parsePowerSource(batt: string): PowerSource
export function parseEnergyMode(text: string): { mode: EnergyMode; modeRaw: string | null }

  sampled: number
  lowPower: number
  onBattery: number
  byMode: Record<string, number>
  bySource: Record<string, number>
}

export function lowPowerWarning(o: {
  live: PowerInfo | null
  samples: readonly PowerInfo[]
}): string | null

export type CallRecord = { /* existing */ power?: PowerInfo }

## Gating

- Local only, in one place: `EvalClient` constructor sets `readPower` only when `profile.queue === 'local'`. Cloud (`haiku-5.5`, `luna-6`) and `fake` records, run summaries and status lines are unchanged: no `power`, no `power` block, no `warning` key, no `pmset` process. Tests above assert the reader is not even called.
- The reader is injected. `EvalClient` and `openRun` have no default, so every existing test (many use the qwen profile) behaves as before and never starts `pmset`. The real reader is the default only at the CLI edge: `runWorker`, `advanceRun` and `runStatus`. Their existing tests use the `fake` model, which `powerWarningFor` and the client gate before any read.
- Off macOS `readPowerInfo` returns unknown and does nothing.
- Cloud default path: the product, `src/`, the cloud profiles and the order of calls are untouched. R2a/R2b cloud runs get call records with no new key at all, so they stay as the spec says.
- The warning is a view, not a state: it is computed when asked, returned in the JSON line, and written nowhere (not `state.json`, not the worker output).

## Risks

- **A local run may be in progress while this lands.** Cross-check update (2026-10-19 23:29): `2026-10-18/run-02-ko` (gpt-oss) has finished (`state.json` status `done`, review written) and no eval worker is running, so this risk applies only if a new local run is started. At survey time it was mid-run. Each `advance` spawns a fresh `tsx eval/novel/cli.ts worker`, which reads the working tree, so an edit shows up in the next advance of that run. A half-finished edit (for example `EvalClient` importing `./power` before the file exists) would break that run's next advance. Implement in the step order above, create `power.ts` first, and keep each intermediate state compiling; or land M1 while no local worker is mid-step. Calls made before the change have no `power`, so that run will show `sampled` smaller than `calls.total`; that is correct, not a bug.
- **The mode mapping is partly assumed** (Evidence, second bullet). A wrong 0 or 2 mislabels automatic or high, but only `low` triggers anything, and `modeRaw` is always stored, so records can be re-read. If a toggle test (user sets Low Power in System Settings, then runs `pmset -g`) shows a different key for Low Power, change only `POWERMODE_MODES` and the fixtures.
- **Automatic may print no key.** If `pmset -g` omits the line at the default, `mode` is `unknown`, never a false `low`. Acceptable.
- **A change in the middle of a long call is not seen.** Only the call start is sampled (a 45-minute proofread could straddle a toggle). The next call's sample shows it. Not fixed: a start-and-end pair would double the record fields for a rare case.
- **`queueMs` of a local call now includes the ~20 ms power read** (step 4 puts the read before `startedMs` on purpose, to keep it out of `durationMs`). The F4 tests that assert `queueMs === 0` use no reader, so they are unaffected.
- **Blind leak is the main correctness risk.** Without step 7 the reviewer sees a `power` block only on local runs. The blind test plus the static `runWorker` guard cover it. (Not in M1's scope: `queueMs` and `waitInclusiveMs` can also differ between local and cloud records; that is F4's behaviour and is left as is.)
- **Status warning language.** English, like the other eval CLI strings; the README text is Korean.
- **Stale scan cost.** `powerWarningFor` parses every call file of a local run (several MB) each time `advance` or `status` returns. That is once per up to 540 s for `advance`. Acceptable.
