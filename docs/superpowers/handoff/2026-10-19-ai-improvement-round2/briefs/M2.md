## Goal

Make the local (Ollama) call record explain where the wall time of a call went, so the next gpt-oss run can show why most of its call time is not prompt reading or token generation. Five changes, all in the eval harness and the Ollama client:

1. Per HTTP attempt, record Ollama's `load`, `prompt_eval`, `eval`, `total` times, `prompt_eval_count`, `eval_count`, `done_reason`, the attempt number, and the length of the thinking (chunk count and character count).
2. Per call, record `unaccountedMs` = wall `durationMs` minus the sum of Ollama's `total_duration` over the attempts (time outside Ollama's timer).
3. Do not compute the prompt speed of a call whose prompt looks cached. Record the flag.
4. In the run summary, mark calls whose output speed is below 70% of the run's usual speed, and add one block that sums where the time went.
5. Keep the blind reviewer blind: the new record block is dropped from the blinded copy.

Product code does not change. Nothing builds `OllamaAiClient` outside `eval/novel/models.ts`, and the new callback is unset in the app (like `onStats`). Cloud runs (Haiku, Luna) get no new data and no new keys.

## Design (TDD, one step at a time; write the step's test first and watch it fail)

### Step 1. Attempt record in the Ollama client (`src/ai/ollama.ts`, test `src/ai/ollama.r2.test.ts`)

1. Add the type (exported, next to `OllamaCallStats`):
   - `task`, `model` (from the done chunk's `model`, else the request model), `attempt` (1 = first request of a call, 2 = the plain JSON retry; a stream is always 1), `done` (a done chunk arrived), `doneReason` (`done_reason` or null).
   - Times in ms, `number | null` (null when no done chunk, or the server left the field out): `loadMs` (`load_duration`), `promptEvalMs` (`prompt_eval_duration`), `evalMs` (`eval_duration`), `totalMs` (`total_duration`). Convert with the existing `NS_PER_MS` and do not round.
   - `promptEvalCount`, `evalCount` (`number | null`).
   - `otherMs` (`number | null`) = `totalMs - (loadMs ?? 0) - (promptEvalMs ?? 0) - (evalMs ?? 0)` when `totalMs !== null`, else null. Not clamped, so the sign is honest. This is time inside Ollama's timer that none of the three named phases holds.
   - `thinkingChunks`, `thinkingChars` (numbers, 0 when none): chunks whose `message.thinking` is a non-empty string, and the sum of their lengths. Only lengths are stored, never the text.
2. `OllamaOptions` gets `onAttempt?: (a: OllamaAttempt) => void` (JSDoc: called once per HTTP attempt that got a response stream, also when the stream failed or was cut; the app does not set it). `ChatResponse` gets `load_duration?: number` and `message?: { content?: string; thinking?: string }`.
3. `readStream` gets an `attempt: number` arg. Inside it count thinking in `handleLine` (before `args.onContent`), remember the done chunk, and report once. Shape:

```ts
let reported = false
const report = () => {
  if (reported) return
  reported = true
  this.settings.onAttempt?.(attemptOf({ ...args, done: doneChunk, thinkingChunks, thinkingChars }))
}
try { /* existing read loop and final flush */ }
catch (error) { report(); await reader.cancel().catch(() => undefined); throw withCauseCode(error) }
report()                                   // before the existing `if (!sawDone) throw streamFailure(...)`
```

   `report()` runs before `reader.cancel()` so the callback fires even if the cancel is slow. The `onStats` call inside `handleLine` stays exactly where it is.
4. Pass the attempt number: `chat()` args gets `attempt: number` and forwards it; `generateObject` passes `1` for the schema attempt and `2` for the JSON retry; `collectStream` passes `1`.
5. Attempts that never got a response stream (connect error, non-2xx status, abort before headers) are not reported (they have no timings). Document this in the JSDoc: the attempt count of a call is the number of reported attempts.

### Step 4. Run summary (`eval/novel/steps/finish.ts`, test `eval/novel/steps/finish.m2.r2.test.ts`)

Constants in `finish.ts`: `SLOW_RATIO = 0.7`, `SLOW_MIN_CALLS = 5`, `SLOW_MIN_OUTPUT_TOKENS = 50`. (decision: "usual" = the run's median output speed, because generation speed is bound by the model, not by the task. Fewer than 5 qualifying calls means no baseline, so no `slow` block.)

1. `slowSummary(calls: CallRecord[])` (exported). A call qualifies when `!call.error`, `call.speed?.source === 'ollama'`, `speed.outputTokensPerSec` is a number and `call.usage.outputTokens >= SLOW_MIN_OUTPUT_TOKENS`. Fewer than `SLOW_MIN_CALLS` qualifying calls returns null. Otherwise `usual = median(rates)` (use the existing `median` in this file) and the result is `{ thresholdRatio: 0.7, usualOutputTokensPerSec: usual, calls }`, where `calls` holds, in `seq` order, each qualifying call with `rate / usual < SLOW_RATIO`, as `{ seq, task, step, outputTokensPerSec, ratio }` (`ratio = rate / usual`). A run with no slow call still returns the block with `calls: []` (checked, none slow). It works on records written before M2, so `resummarize --date 2026-10-18` fills it for run-01.
2. `ollamaSummary(calls)` (exported). Rows = calls with `call.ollama` and at least one attempt. Returns null when there are no rows. Otherwise:

```ts
{
  calls: number            // rows
  attempts: number         // all attempts of the rows
  retried: number          // rows with more than one attempt
  lengthCut: number        // attempts with doneReason === 'length'
  cacheSuspected: number   // rows with ollama.promptCacheSuspected
  thinking: { chunks: number; chars: number }
  timed: {                 // only rows whose ollama.unaccountedMs is not null
    calls: number
    wallMs: number         // sum of durationMs
    loadMs: number; promptEvalMs: number; evalMs: number; otherMs: number  // sums over their attempts, null counts as 0
    unaccountedMs: number
    unaccountedShare: number | null   // unaccountedMs / wallMs, null when wallMs is 0
    unaccountedByTask: Record<string, number>
  }
}
```

   The identity `wallMs = loadMs + promptEvalMs + evalMs + otherMs + unaccountedMs` must hold for `timed` (it does, because `otherMs` and `unaccountedMs` are unclamped).
3. `speedSummary` returns the existing four keys plus `...(slow ? { slow } : {})` and `...(ollama ? { ollama } : {})`. When neither applies (cloud runs, old records) the result is exactly what it is today.
4. `SpeedSchema` gets `slow` and `ollama` as `.optional()` zod objects with the same shapes (`step: z.string().nullable()`, counts `CountSchema`, ms and ratios `z.number()`, `unaccountedShare: NullableNumberSchema`). Old summaries still parse.

## Gating (local-only behaviour, cloud default path)

- Ollama client: `onAttempt` is optional and unset in the app, exactly like `onStats`. Without a callback the only new work is counting thinking chunks, which costs nothing and changes no output. The product never builds `OllamaAiClient`.
- Eval client: attempts exist only when an Ollama client reports them, so cloud and fake profiles never get an `ollama` key. `promptKey` and the `sentPrompts` set are only filled when `profile.provider === 'ollama'`. `speedOf`'s new argument only matters in its Ollama branch; the wall branch is untouched.
- Summary: `speed.slow` needs 5 Ollama-source ok calls; `speed.ollama` needs at least one record with an `ollama` block. Cloud runs (R2a, R2b) produce neither, so their `run-summary.json` stays as the spec expects (no change to the cloud default path).
- Blind copy: `ollama` is dropped, and the new summary blocks sit inside `speed`, which is already dropped.

## Risks

- A tiny prompt time on gpt-oss may be a misreported timer, not a cache hit (the first call of `run-02-ko` is already at 69,649 tokens/s on a fresh model). The flag only says "do not trust this rate". The raw `promptEvalMs` stays in the attempt, and `otherMs` and `unaccountedMs` show where the time actually went.
- Partial cache hits on a different prompt with a shared prefix are not caught (qwen `026` at 859 tokens/s is caught only because its prompt equals `025`'s). The medians are robust to a few such calls. The repeat set is per process, so the first repeat after a resume is not flagged.
- Thinking length counts only `message.thinking` chunks. If an Ollama version puts thinking inline as `<think>` in `content`, the count is 0 for that run (the client still strips it with `stripThink`). Look at `thinkingChars` against `evalCount` before drawing conclusions.
- Matching by task name relies on one call per task at a time (the F4 lane and sequential streams). A new track that runs two local calls of the same task together would mix their attempts.
- Merge order inside the M batch: M1 and M4 also add fields to `CallRecord`, `Prepared`, the `settle` record literal and the `blindCallRecord` delete list (M1 power mode, M4 effort and token limits are fingerprints too). Implement in the spec order and re-read those symbols before editing; add keys, never replace the others. Each of them must add its own blind test; M2's covers only `ollama`.
- Record size: about 250 bytes per attempt; at most two attempts per call. No concern.
- `unaccountedMs` and `otherMs` can be slightly negative. Do not clamp; tests assert the sign for `unaccountedMs`.

## Open questions (default chosen)

1. Per-call flag for slow calls, or a summary list? Default: summary list (`speed.slow`), because "usual" needs the whole run and `resummarize` must not rewrite `calls/`. Calls are joined by `seq`.
2. Usual speed per task or per run? Default: per run (median of ok Ollama calls with at least 50 output tokens), minimum 5 calls.
3. Rate ceiling 5,000 tokens per second, strictly above. Default as in evidence; a constant in `ollama-detail.ts`, easy to change after the first local run.
4. Count attempts that failed before any response stream (connect error, HTTP error)? Default: no. They have no timings and the error is already in `record.error`.
5. Should `eval/novel/agents/summary.md` get a column for unaccounted time? Default: not in M2 (M3 owns that file). Suggest to M3: add one sentence telling the summary agent to read `speed.ollama.timed` and `speed.slow` when present.
6. Per-task unaccounted breakdown only in the summary, not in the record. Default yes (`unaccountedByTask`).
