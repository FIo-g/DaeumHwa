# 본선 데모 준비 설계 (2026-11-03)

## 왜

본선 결과물에 "시연 가능한 데모"가 들어 있다. 지금은 심사위원이 가입하고, 설정을 입력하고, 원고를 써야 회차 점검 결과를 본다. 버튼 하나로 다음화의 핵심(위키 근거를 인용하는 설정 점검)을 바로 보여 줘야 한다.

## 2026-11-03 점검에서 확인한 사실

- 운영 사이트(daeumhwa.vercel.app)의 AI 호출은 정상이다. 시험 계정으로 회차 점검을 실제로 돌렸고, 25초 만에 심어 둔 손 방향 충돌을 찾았다.
- 운영과 로컬 프로덕션 빌드 모두 집필 화면의 서버 액션이 500을 낸다. 서버 로그: `A "use server" file can only export async functions, found object.`
  - 원인: `src/server/actions/ai-features.ts` 가 zod 객체 `PlanDraftSchema` 를 export한다(809973e).
  - 증상: 자동 저장 실패("오프라인: 이 기기에 임시 저장됨"), 점검 뒤 위키 후보 대화상자가 비어 있음, "잠시 후 다시 시도해 주세요." 토스트.
  - 영향: e2e `core-flow`, `editor-scroll` 실패. 샘플 체험도 이 화면에서 시연하므로 가장 먼저 고친다.
- e2e `interview` 실패: AI 스텁 프로세스에 `AI_SPEECH_STYLE=off` 가 없다. 그래서 스텁은 말투 규칙이 켜진 system 프롬프트를 기대하고, 서버는 끈 프롬프트를 보내 HTTP 400이 난다.
- 운영의 위키 근거 칸에 `[F1][확정] 서윤은 왼손잡이다.` 처럼 AI가 내부 ref 태그까지 옮겨 적은 문장이 보인다. 설명에도 "위키 F1에 따르면"이 나온다.
- 평가용 `eval/fixtures/continuity-planted` 의 심은 오류 4곳은 Haiku와 Luna가 모든 effort에서 4/4 찾았다(`docs/eval/harness/2026-10-20-stage0-baseline.md` 6장). 1~3화만 쓰면 오류는 3곳이다.

## 할 일

1. **운영 버그 수정 (T0)**: `'use server'` 파일에서 함수가 아닌 export를 없앤다. 같은 실수를 막는 시험을 더한다. e2e 스텁에 `AI_SPEECH_STYLE=off` 를 준다. e2e 7개가 모두 통과해야 한다.
2. **샘플 작품 원클릭 체험 (T1)**
   - `내 작품` 화면의 `샘플 작품으로 체험하기` 버튼 하나로 다음이 든 작품을 만든다.
     - continuity-planted의 인물·장소·물건 카드 5개
     - 확정 사실 5개
     - 원고 1~3화(오류 3곳: 2화 나이, 3화 층수, 3화 손)
     - 떡밥 3개
   - 바로 3화 집필 화면으로 가서 점검 탭을 열고 회차 점검을 자동으로 돌린다.
   - 화면 위쪽 안내 띠가 오류를 심은 곳(2화 1곳, 3화 2곳)을 알려 주고, 2화 점검과 설정 보드로 가는 링크를 준다.
3. **근거 문구를 위키 원문으로 (T2)**
   - 사실을 인용한 지적이면 근거 칸에 그 사실의 원문(`facts.content`)을 그대로 넣는다.
   - 카드만 인용한 지적이면, AI 문구가 카드 원문에 그대로 있을 때만 쓰고 없으면 카드 요약을 쓴다.
   - 설명 문구에 새어 나온 ref 태그(`[F1]`, `위키 F1` 등)를 지운다.
4. **연재 일정 수정 화면 (T3)**: 일정 목록의 각 항목에 `수정` 을 둔다. 이미 있는 `updateScheduleItemAction` 을 부른다.
5. **사실의 유효 회차 입력 (T4)**: 사실 추가·수정 폼에 `유효 시작 회차`, `유효 끝 회차` 입력을 더한다. 서버도 범위를 검증한다.
6. **README 갱신 (T5)**: lean harness가 2026-10-30에 main에 합쳐졌다(de76da9). "아직 main에 합쳐지지 않았습니다" 같은 문구를 고치고, 샘플 체험을 기능 목록에 더한다.

## 하지 않는 것

- 초대 링크: 만료와 취소가 이미 있다.
- 떡밥 기한 초과를 점검 결과에 띄우기: 선택 사항이라 이번에는 하지 않는다. 샘플의 떡밥 하나를 기한 초과로 만들어 떡밥 장부에서 보이게만 한다.
- 새 패키지, DB 마이그레이션.

## 설계 판단 (사용자가 맡긴 결정)

- (설계 판단) 3화로 바로 간다. 오류가 2곳이라 한 번의 점검으로 가장 많이 보여 준다. 그중 "종루지기가 열한 층"은 카드 이름이 복합어 안에 숨은 어려운 경우다.
- (설계 판단) 자동 점검은 `?demo=1` 이 붙은 집필 화면에서 한 번만 돈다. 시작하면 주소에서 `demo` 를 지워, 새로고침해도 AI를 다시 부르지 않는다. 안내 띠는 처음 받은 화면에 남는다.
- (설계 판단) 자동 점검에서는 위키 후보 대화상자를 저절로 띄우지 않는다. 점검 결과를 가리지 않게 하려는 것이다. 후보는 평소처럼 승인 대기에 남는다.
- (설계 판단) 샘플 데이터는 앱 코드 안의 상수로 둔다. 배포 번들에 `eval/` 이 없기 때문이다. 시험 하나가 그 상수의 원고와 사실이 평가 세트 파일과 같은지 지킨다.
- (설계 판단) 떡밥 3개 가운데 하나는 회수 목표를 2화로 두어 `회수 목표 지남` 이 보이게 한다.
- (설계 판단) 실행 방식: Opus가 계획을 쓰고, Sonnet 에이전트가 작업마다 OpenCode를 부려 구현한다. 모델은 deepseek-v4.1-flash-free, 다음 glm-5.3-flash-free, 막히면 muse-spark-1.3-contributor 순이다. 마지막 검토는 Sonnet이 한다. push와 배포는 사용자에게 먼저 묻는다.
