# AI 개선 2라운드 설계

작성: 2026-10-19 · 브랜치: `feat/ai-improvement-round2`(`feat/ai-improvement-local` 끝 2eaa797에서 갈라짐)

## 1. 배경과 목표

- 1라운드 개선 트랙(A~J, HX1~HX5, C, D, F1~F4)은 구현, 리뷰, 수정까지 끝났다. 효과는 아직 재지 않았다.
- 같은 날 추가 조사를 했다. Haiku 6개가 관점을 나눠 찾고, Sonnet이 정리하고, Opus가 근거를 확인했다. 사용자는 그 목록을 "전부 다 진행"하라고 했다(2026-10-19).
- 목표는 그대로다. 경량 모델만으로 출판 가능한 1화를 낸다.
  - 출판 가능은 T1~T7을 모두 통과하고, Q 평균이 3.75 이상이며, 2점 이하 항목이 없는 상태다.
  - 1단계는 클라우드, 2단계는 로컬이다.
- 이번 라운드의 순서:
  1. 측정을 바로잡는다.
  2. 지금 브랜치(A~J 반영)를 클라우드로 다시 잰다(전).
  3. 추가 앱 개선을 넣는다.
  4. 다시 잰다(후). 개선 몇 가지는 따로 켠 비교 실행으로 잰다.

### 제외 (이유)

- **조사 1-2 본안, 2-1, 3-3, 1-8의 effort 낮춤, 1-3 필터안:** Opus 비판 단계에서 뺐다.
  - 제품에 로컬 공급사가 없다.
  - 이미 구현됐다.
  - 사용자 결정과 충돌한다(작가 지침의 분량 기준은 기록만, 클라우드 effort는 high).
  - 근거가 틀렸다.
- **1-16 이름 잘림 방침:** 사용자가 정할 일이다. `종루` 고정 테스트(736/848)와 충돌해서 1라운드에서 일부러 남겼다. 기록만 한다.
- **2-5 인터뷰 프롬프트 누적:** 상한이 이미 있고(`interview.ts`의 RECENT 6, 답 600자, COVERED 120) 효과가 낮다. 기록만 한다.
- **로컬 실행 전부:** 사용자가 오늘은 gpt-oss 한국어까지만 하라고 했다. 다음 로컬 세션에서 할 일은 README에 명령으로 적는다.
  - gpt-oss 영어, exaone 한국어·영어
  - `--helper-think` 비교(2-2)
  - gpt-oss 시간 원인 확인(2-3, M2 기록으로)
  - qwen 온도 0.6 비교(2-7)
- **같은 본문 재채점(3-4의 재채점), 반복 실행:** 이번에는 두 번째 검토자만 붙인다. 반복 실행은 규칙만 적는다.

## 3. 그대로 지키는 사용자 결정

- 클라우드 effort는 high다. 모든 실행은 1화다. 패키지는 바꾸지 않는다. 로컬 모델은 한 번에 하나만 돈다.
- B 말투 기능은 기준 실행에서 끈다. `bible.json`의 답 은행은 고치지 않는다.
- `author.md`의 짧은 초안 판단 기준은 고치지 않는다.
- 로컬 전용 동작은 공급사(`isLocalProvider`)나 프로필(`queue === 'local'`)로 막는다. 클라우드 기본 경로는 이 라운드의 P 항목이 의도해서 바꾸는 것 말고는 그대로 둔다.
- 사용자에게 보이는 문구는 한국어로, 식별자와 주석은 영어로 쓴다. `AppError`/`ActionResult`, `change_log`, AI는 위키 표에 직접 쓰지 않는다.
- push는 사용자가 한다. `git add -A`는 쓰지 않는다.

## 4. 설계 판단

- **브랜치.** 1라운드 PR(`feat/ai-improvement-local`)을 키우지 않으려고 새 브랜치에 쌓는다.
- **실행 위치.** 실행은 고정된 커밋의 별도 worktree에서 돌린다. 진행 중인 실행에 코드 변경이 섞이지 않게 하려는 것이다.
  - R2a는 `../DaeumHwa-r2a`, R2b와 비교 실행은 `../DaeumHwa-r2b`에서 돌린다.
  - 결과 폴더 `eval/results`는 메인 체크아웃 것과 연결한다.
- **M3 판정선 근처.** Q 평균이 3.65~3.85이거나 T 실패가 1건뿐이면 두 번째 Sonnet 검토자가 독립으로 채점한다(`review-2.md`). 요약은 두 판정을 모두 적고, 둘이 다르면 "판정 불일치"로 표시한다.
- **M5 말투 실행의 답 은행.** 실행을 만들 때 `bible.json`의 인물 `voice`를 답 은행의 해당 인물 답에 덧붙인 사본을 실행 폴더에 `bible.json`으로 쓴다. 작가 지침에는 "실행 폴더에 `bible.json`이 있으면 그것을 읽는다"를 더한다. 원본 픽스처는 그대로이고, 기준 실행에서 작가가 하는 일도 같다.
- **M4 `--product-limits`.** effort는 바꾸지 않는다(사용자 결정 high). maxTokens만 작업 값으로 둔다.
- **P4 규칙.** 두 규칙을 함께 넣고 R2b에서 같이 잰다. 규칙마다 따로 비교하면 클라우드 실행이 규칙당 4개씩 늘어난다. 효과가 섞이는 한계는 결과 문서에 적는다.
- **P6 화면.** 초안이 끝난 뒤 "다듬기" 버튼을 둔다. 결과는 바뀐 문장을 표시한 미리보기로 보이고, 작가가 적용하거나 버린다. 자동 적용은 하지 않는다. 세부는 기존 맞춤법 패널의 적용 흐름을 따른다.
- **P9 범위.** 로컬 eval 재시도만 다룬다. "거절 사유를 재초안 프롬프트에 넣기"는 작가 지침의 "지시문 불변" 규칙과 충돌해서 하지 않는다.
- **P13 측정.** `eval:continuity`는 실제 API를 쓴다. 클라우드 Haiku로 P13 전과 후에 한 번씩 돌린다.
- **M7 반영 기준.** 임계값은 저장된 실행의 통과·실패가 검토서 판정과 더 잘 맞을 때만 바꾼다. 그렇지 않으면 보고서에 남기고 그대로 둔다. 브리프 단계의 재계산 결과 사실 중복 유사도만 0.8에서 0.7로 낮추고, 이 상수 변경은 R2a 뒤 P 묶음 첫 커밋으로 넣는다.
- **교차 점검 결정(2026-10-19).**
  - P3의 게이트는 `twoStepOn(ctx)`와 `beats.json`이다. 기본 클라우드 경로는 그대로이고, R2t에서 P1~P3이 함께 잰다.
  - P10은 세기만 한다. 결과 문서에서 "추출 거절 수"의 변화를 P10의 효과로 보지 않는다.
  - M3은 Q5 기준에서 문체 카드 규칙을 빼고 Q6~Q8로 옮긴다. 그래서 1라운드 대비 Q5와 Q6~Q8 차이는 방향만 본다. 1라운드 T2는 M3의 README 표로 새 범위에 맞춰 다시 읽는다(재채점 아님).
  - R2b 대 R2a에는 P4·P5·P7(초안·독자 프롬프트), P11, M7 상수, P15가 섞인다. R2t에는 두 단계 초안과 P1~P3, 장면 다시 쓰기가 섞인다. 결과 문서에 적는다.

## 5. 작업 순서

1. 이 설계서와 실행 계획을 커밋한다.
2. 트랙마다 브리프를 쓴다(Sonnet, 코드 조사 포함). 브리프: `docs/superpowers/handoff/2026-10-19-ai-improvement-round2/briefs/`, 조사 원문: 같은 폴더의 `survey.md`, 교차 점검: `cross-check.md`.
3. M 묶음을 구현한다(Haiku TDD, 순서대로) → 트랙별 검토(Haiku) → 마감 조건(Sonnet).
4. R2a worktree를 만들고 클라우드 4개를 시작한다. 실행은 백그라운드에서 이어진다.
5. P 묶음을 구현한다(Haiku TDD, 순서대로) → 트랙별 검토(Haiku) → 통합(Sonnet) → 전체 리뷰(Opus) → 수정.
6. R2b worktree에서 R2b와 비교 실행(R2s, R2t, R2l)을 하고, R2c 재현율을 잰다.
7. 날짜 폴더별 요약과 전후 비교 문서를 쓴다(Sonnet). 메인 체크아웃의 `docs/eval/novel/`에 커밋한다.

- R2l 대 R2b: 잘린 초안 수, T3, T7.
- R2c: 심은 숫자 오류 검출률, 헛지적 수.

## 7. 위험

- **비용.** 클라우드 실행 14개는 실행마다 Sonnet 에이전트 약 57개를 쓴다. OpenCode 5시간 한도에 걸리면 실행이 `paused-limit`로 멈추고 `RESUME.md`가 생긴다. 같은 인자로 다시 부르면 이어서 돈다.
- **전원.** 맥은 전원을 연결하면 저전력 모드가 된다(`pmset` AC `powermode 1`). 클라우드 실행에는 영향이 작고, 로컬 측정은 M1 기록으로 구분한다. 설정은 사용자만 바꿀 수 있다.
- **P4·P5는 클라우드 초안 프롬프트를 바꾼다.** B의 "말투를 끄면 바이트 단위로 같다" 고정 테스트는 새 기준 문자열로 고친다. 동작을 되돌려 맞추지 않는다.
- **P6은 새 화면 기능이다.** 맞춤법 패널과 같은 적용 방식이어야 하고, 작가가 누르기 전에는 원고를 바꾸지 않는다.
- **같은 파일을 여러 P가 고친다.** `draft-chapter.ts`는 P4·P5, `draft-beats.ts`는 P1·P2, 추출은 P10·P11·P15다. 그래서 구현은 한 작업 트리에서 순서대로 한다.
