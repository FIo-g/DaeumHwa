# 인터뷰 연속 질문 · AI 안정성 · UX 수정 설계 (2026-10-18)

기존 MVP 설계(`2026-10-16-daeumhwa-mvp-design.md`) 위에 얹는 수정 설계. 테스트 사용자 보고와 코드 조사에서 나온 문제를 고친다. "(설계 판단)"은 사용자가 맡긴 판단으로 오케스트레이터가 정한 것이다.

## 1. 배경

테스트 사용자 보고(요약):

- 인터뷰: 8개 핵심 질문 뒤 "더 정리해 두고 싶은 설정이 있나요?"가 반복되다 1번 질문으로 돌아감(1차 13문답, 2차 21문답). 그 결과 같은 인물 카드가 따로 생김(노은하/전직, 주인공/한시우).
- 카드 파싱: "전직 시계탑 수리공 노은하"의 이름이 "전직"으로 잘림. 한시우 설명이 "전전대 관리자였던 인물. 한기준의 아들"로 주체가 뒤바뀜(전전대 관리자는 한기준).
- 에러 처리: 2차 인터뷰 중 "잠시 후 다시 시도해 주세요." 후 다음 질문이 먹통, 새로고침하니 ERR_CONNECTION_REFUSED(서버 다운). 회차 점검 "점검 중… (AI)"가 20초 넘게 멈추고 취소 버튼이 없음. AI 초안도 같음.
- UX: 인터뷰 안내는 "승인 대기에서 확인"이라는데 실제로는 인라인 승인으로 바로 위키에 반영되고 승인 대기는 0건. 회차 제목이 "1화 1화"로 겹침. 목표 5,500자 중 4,265자(78%)인데 완료 가능. 관계 그래프에 618×515 캔버스 3개가 겹쳐 보임.

코드 조사 결과:

- 반복 질문 "더 정리해 두고 싶은 설정이 있나요?"와 "첫 한글 단어 = 이름" 규칙은 데모(가짜 AI) 모드의 고정 출력이다(`src/ai/tasks/interview-question.ts`의 `fakeQuestion`, `interview-extract.ts`의 `firstNameToken`). 보고는 데모 모드에서 나온 것으로 보인다.
- 1번 질문 회귀는 실제 AI에도 해당한다. 질문 생성에 최근 10문답만 넘기므로(`HISTORY_LIMIT = 10`) 그 앞의 주제는 AI가 모른다. 이전 인터뷰 세션의 주제도 넘기지 않는다.
- 추출 결과의 카드 중복 판정은 승인된 위키 카드만 본다. 아직 승인하지 않은 `entry_create` 제안은 보지 않으므로 같은 인물 후보가 답마다 새로 생긴다. 새 후보의 별칭이 기존 카드 이름과 같아도 중복으로 보지 않는다.
- 인터뷰 질문·답 처리는 Server Action으로 AI를 부른다. Next는 한 클라이언트의 Server Action을 한 번에 하나씩 처리하므로, AI가 오래 걸리면 그 뒤의 모든 액션(자동 저장 포함)이 줄을 서서 화면이 먹통이 된다. AI 호출에는 시간 제한이 없다(SDK 기본 10분 × 재시도 2회). 취소 경로도 없다.
- 회차 제목: 새 회차와 가져오기 회차의 기본 제목이 `"{n}화"`이고, 표시 함수 `chapterLabel`이 다시 `"{n}화 "`를 붙인다.
- 관계 그래프: cytoscape는 원래 캔버스 3장(선택 상자·드래그·노드 층)을 겹쳐 그린다. 같은 크기의 캔버스 3장은 정상 구조일 가능성이 높다. 인스턴스가 하나만 붙는지 확인한다.
- 서버 다운: 로그가 남아 있지 않아 원인을 확인하지 못했다. Next 16은 처리되지 않은 Promise 거부로 프로세스를 죽이지 않는다. 재현 조사가 필요하다.

## 2. 목표

1. 인터뷰는 지금처럼 한 번에 한 질문씩 진행하되 끝없이 이어지고, 이미 다룬 질문으로 돌아가지 않는다. AI가 설정이 충분한지 판단해 빈 설정 질문 또는 다음 화·스토리라인 질문을 한다. 인터뷰는 연재 중 언제든, 몇 번이든 할 수 있다. (사용자 결정)
2. 인터뷰 답에서 같은 인물의 카드 후보가 두 번 생기지 않는다. 이름에 직함·수식어가 붙거나 설명의 주체가 뒤바뀌지 않도록 추출 지시문과 코드 가드를 보강한다.
3. 데모 모드(정해진 답을 내는 가짜 AI)를 앱 코드에서 지운다. (사용자 결정)
4. 모든 AI 호출에 시간 제한과 취소가 있고, 실패해도 다시 시도할 수 있다. 오래 걸리는 AI 호출이 다른 작업을 막지 않는다.
5. 서버 다운의 원인을 재현으로 찾아 고친다. 재현되지 않으면 그 사실과 시도한 내용을 보고한다.
6. UX: 승인 안내 문구를 실제 동작에 맞춘다. 회차 제목 중복을 없앤다. 목표 분량에 못 미친 회차를 완료할 때 경고한다. 관계 그래프의 중복 렌더 여부를 확인하고, 중복이면 고친다.

## 3. 비목표

- AI 답 품질 평가 체계(실제 경량 모델 대상 평가). 다음 과제로 미룸. (사용자 결정)
- 로컬 AI 모델 지원.
- 회차 제목 패턴 강제(예: "00:00 멈춘 종"). 작품마다 다른 스타일이므로 강제하지 않는다. (설계 판단)
- 인터뷰 종료 시 별도 선택 화면. 기존 "인터뷰 끝내기" 버튼을 유지한다. (사용자 결정: "기존과 동일하게 진행")
- 다음 화 계획을 담는 새 저장 공간(테이블·화면). 방향 답은 기존 떡밥·설정 후보로 정리한다. (설계 판단)
- 패키지 추가·삭제·업그레이드.

## 4. 안티 목표 (기술적으로 돌아가도 실패인 것)

- 테스트가 실제 AI API를 부른다.
- 앱 런타임 코드에 가짜 AI 경로가 남는다(환경 변수로 켤 수 있는 경로 포함).
- AI가 위키 테이블을 직접 쓴다. 위키 변경은 작가 행동 또는 승인된 제안으로만, `change_log`와 같은 트랜잭션으로 기록한다(기존 원칙 유지).
- 인터뷰가 이미 한 질문을 되풀이하거나 1번 주제로 되돌아간다.
- 취소한 AI 작업이 `ai_runs`에 `running`으로 남아 동시 실행 한도(3개)를 잡아먹는다.

## 5. 결정 사항

### A. 데모 모드 삭제

- `AI_PROVIDER`는 `anthropic`, `opencode`만 인정한다. `fake`를 포함한 그 밖의 값은 알 수 없는 값으로 보고 키 유무로 정한다(기존 경고 유지). 키가 둘 다 없으면 제공자가 없다.
- 제공자가 없으면 AI 기능은 `AppError('AI_ERROR', 'AI 키가 설정되지 않아 AI 기능을 쓸 수 없습니다.')`로 실패한다. 앱 상단 데모 배너는 "AI 키가 설정되지 않았습니다" 안내 배너로 바꾼다(키가 있으면 숨김). 집필 화면의 `demo` 플래그는 없앤다.
- 가짜 출력 함수(`AiTaskDef.fake`, 각 task 파일의 `fake*` 함수, `FakeAiClient`)는 앱 코드에서 지우고 테스트 전용 코드(`src/test/`)로 옮긴다. 단위 테스트는 지금처럼 가짜 클라이언트를 주입한다. (설계 판단)
- 테스트용 가짜 클라이언트가 task별 출력을 고를 수 있도록, 클라이언트 호출 인자에 `task: { name, input }` 정보를 싣는다. 실제 클라이언트는 이 값을 쓰지 않는다. (설계 판단)
- 테스트 코드가 앱 번들로 새지 않도록, 테스트가 아닌 파일이 `@/test/`를 import하지 못하게 ESLint로 막는다. (설계 판단)
- E2E는 Anthropic Messages API를 흉내 내는 로컬 HTTP 스텁 서버로 돌린다. AI 모델은 쓰지 않고, 요청한 task에 맞는 고정 출력을 돌려준다. 앱은 `AI_PROVIDER=anthropic`, `ANTHROPIC_BASE_URL=<스텁 주소>`, 더미 키로 뜬다. (사용자 확인)
- `eval/run-continuity.ts`의 `--fake` 옵션은 테스트용 가짜 클라이언트를 쓰도록 import만 바꾼다(평가 도구는 앱 런타임이 아니다).
- 문서(`.env.example`, README, `CLAUDE.md`의 테스트 안내)에서 데모 모드 설명을 지우거나 고친다.

### B. 인터뷰 연속 질문

- 질문 생성 입력에 다음을 넣는다.
  - 작품 정보(기존).
  - 위키 요약: 종류별 카드 수, 카드 이름·종류·사실 수·요약 앞 40자(최대 80개), 열린 떡밥 제목과 회수 목표 회차(최대 30개). 카드가 얕은지 AI가 판단할 수 있게 사실 수와 요약을 넣는다. (설계 판단)
  - 연재 재료: 최신 회차 번호, 최근 회차 요약(최근 5개, 요약이 있는 것), 최근 독자 반응 요약(최근 회차들의 `reader-sim` 결과에서 짧게, 최대 3개), 열린 회차 점검 지적 수.
  - 다룬 질문 목록: 이 작품의 **모든 인터뷰 세션**의 모든 질문(주제, 질문 앞 120자, 답 앞 80자, 건너뜀 여부, focus). 오래된 것부터. 길면 최근 120개만 넣고 버린 개수를 프롬프트에 적는다. 답 앞부분이 있어야 오래전 답도 이어서 물을 수 있다. (설계 판단)
  - 현재 세션 최근 대화: 최근 6개 문답(답은 600자까지).
- 출력은 `{ focus: 'setting' | 'story', topic, question, rationale }`.
  - AI가 판단한다: 핵심 설정(주인공, 주요 인물, 세계관 규칙, 주요 장소, 중심 갈등, 떡밥, 결말 방향, 문체) 중 비었거나 얕은 것이 있으면 `setting` 질문, 충분하면 `story` 질문(다음 화를 어떻게 할지, 스토리라인을 어떻게 끌고 갈지). `story` 질문은 회차 번호, 떡밥 이름, 독자 반응 같은 구체적인 재료를 짚는다.
  - 이미 다룬 질문은 되풀이하지 않는다. 같은 주제를 다시 다룰 때는 이전 답을 바탕으로 한 걸음 더 나아간 질문만 허용한다.
- 서버 가드: 생성된 질문을 정규화(공백·문장부호 제거)해 이 작품의 이전 질문과 같으면, "이미 한 질문"이라는 메모를 붙여 한 번 다시 생성한다. 두 번째도 같으면 그대로 쓴다(실패시키지 않는다). (설계 판단)
- 질문은 끝없이 이어진다. 끝내기는 기존 "인터뷰 끝내기" 버튼으로 한다. 끝낸 뒤 "새 인터뷰 시작"으로 언제든 다시 할 수 있다(기존 동작 유지). 새 세션도 이전 세션들의 다룬 질문을 본다.
- `interview_turns`에 `focus` 열(`'setting' | 'story'`, 기본값 `'setting'`)을 추가한다. 질문 카드에 작은 표시로 "설정 채우기" 또는 "다음 전개"를 보여 준다. (설계 판단)
- 답 추출에 focus를 넘긴다. `story` 답에서는 작가가 정한 앞으로의 전개를 떡밥 후보(`threads`, kind `planted` → 인터뷰 출처라 `planned` 상태)로 정리하고, 답에 회차가 나오면 `targetChapterPosition`을 채운다. 작가가 망설이며 말한 아이디어는 떡밥이 아니라 사실 후보(`facts`, `suggestedStatus: 'undecided'`, 주어는 관련 인물 카드 이름)로 둔다. 떡밥에는 새 상태를 만들지 않는다. (설계 판단)
- 떡밥 중복: 인터뷰 추출에도 기존 떡밥(보관되지 않은 것)과 승인 대기 중인 `thread_create` 제목을 넘긴다(프롬프트의 `<threads>`). 같은 제목의 떡밥 후보는 다시 만들지 않는다. 이미 있는 떡밥의 회수 목표 회차를 바꾸는 제안은 지원하지 않는다(그런 답은 사실 후보로만 남는다). (설계 판단)
- 질문 생성과 답 처리(AI를 부르는 두 동작)는 Server Action 대신 route handler(`POST /api/works/[workId]/interview/next`, `.../interview/answer`)로 옮긴다. 회차 점검과 같은 방식이다. 시작·건너뛰기·끝내기는 Server Action으로 둔다.

### C. 중복 카드와 추출 품질

추출 지시문(인터뷰·회차 점검·원고 가져오기의 추출 task가 함께 쓰는 공통 규칙):

- `name`에는 고유 이름만 쓴다. 직업·직함·수식어는 이름에 넣지 않고 `summary`나 `fields`에 넣는다. 예: "전직 시계탑 수리공 노은하" → name "노은하", summary "전직 시계탑 수리공".
- "주인공", "남주", "여주", "그", "그녀" 같은 역할어나 대명사는 이름이 아니다. 답에 이름이 없으면 카드를 만들지 않는다. 그 역할의 인물이 `<known>`에 있으면 그 이름을 쓴다.
- `summary`는 그 카드의 대상 자신에 대한 설명이다. 다른 인물과의 관계를 적을 때 주어를 바꾸지 않는다. 예: "한기준은 전전대 관리자였고 한시우는 그의 아들이다" → 한기준 summary "전전대 관리자", 한시우 summary "한기준의 아들".
- 이미 있는 카드와 승인 대기 중인 카드 후보 모두 `<known>`으로 넘긴다.

코드 가드(`extractionToProposals`):

- 승인 대기 중인 `entry_create` 제안의 이름·별칭도 기존 이름으로 본다. 같은 이름의 후보를 다시 만들지 않는다. 이 이름에 묶이는 사실의 `entryId`는 기존처럼 `null`이다(승인 대기 카드는 아직 id가 없다).
- 새 후보의 별칭이 기존 카드(또는 대기 후보)의 이름·별칭과 같으면 새 카드를 만들지 않는다. 기존 위키 카드라면 새 이름과 별칭을 그 카드의 별칭으로 더하는 `entry_update` 제안을 낸다(이미 별칭이면 생략).
- 띄어쓰기가 있는 이름은 마지막 어절(조사 제거)도 대조한다. "시계탑 수리공 노은하"의 마지막 어절 "노은하"가 기존 카드나 같은 추출 결과의 다른 후보와 같으면 그 대상으로 본다.
- 역할어 목록(주인공, 남주, 여주, 남자 주인공, 여자 주인공, 악역, 조연, 화자, 나, 그, 그녀, 그들)과 정확히 같은 이름의 카드 후보는 버린다. 주어가 역할어인 사실 후보와 한쪽 끝이 역할어인 관계 후보도 버린다. (설계 판단)
- 마지막 어절 대조는 인물 카드끼리만 한다(장소 "북쪽 시계탑"이 "시계탑" 카드에 합쳐지지 않게). 마지막 어절로 합쳐진 긴 이름은 별칭으로 더하지 않는다. (설계 판단)

### D. AI 시간 제한과 취소

- 클라이언트 호출 인자에 `signal?: AbortSignal`, `timeoutMs?: number`를 둔다. Anthropic SDK와 Responses 클라이언트 모두 요청에 signal과 timeout을 넘긴다. SDK 재시도는 1회로 줄인다.
- 기본 시간 제한: 구조화 출력 120초, 스트리밍 초안 280초, 원고 가져오기 추출 240초. task가 `timeoutMs`로 바꿀 수 있다. (설계 판단)
- 시간 초과는 `AppError('AI_ERROR', 'AI 응답이 너무 오래 걸려 멈췄습니다. 다시 시도해 주세요.')`.
- 취소: 새 오류 코드 `CANCELLED`(메시지 "취소했습니다.")를 둔다. route handler는 `request.signal`을 서비스로 넘기고, 서비스는 `runAiTask`/`startAiStream`의 meta로 넘긴다. 취소되거나 시간이 초과된 실행은 `ai_runs`에 `error` 상태와 메시지로 기록한다(`running`으로 남기지 않는다).
- 클라이언트: `postAction`이 `signal`을 받는다. 중단되면 `CANCELLED` 결과를 돌려주고, `runAction`은 `CANCELLED`에는 오류 토스트를 띄우지 않는다.
- Server Action으로 AI를 부르던 스토리 방향 조언(`runDirectionAdviceAction`)과 문체 카드 제안(`suggestStyleCardAction`)도 route handler로 옮긴다. 원고 가져오기는 이미 작업(job) 방식이라 그대로 두고 시간 제한만 적용한다. (설계 판단)
- 화면: 회차 점검, AI 초안, 교정(AI), 독자 반응, 스토리 방향 조언, 문체 카드 제안, 인터뷰 질문 생성·답 처리에서 실행 중에는 경과 초("점검 중… 12초")와 "취소" 버튼을 보여 준다. 취소하면 바로 원래 상태로 돌아오고 "취소했습니다." 안내를 띄운다.
- AI 초안을 취소하면 그때까지 나온 글은 화면에 남기고 "현재 원고 끝에 붙이기"만 허용한다. "새 회차로 만들기"는 끝까지 완성된 초안에만 허용한다(기존 규칙: 완료된 run만 회차로 만든다).
- 실패 후 다시 시도: 인터뷰 질문 생성이 실패하면 질문 자리에 오류 문구와 "다시 시도" 버튼을 보여 준다. 답 처리가 실패하면 입력한 답을 지우지 않는다.

### E. 서버 다운 조사

- 스텁 AI 서버(느린 응답 모드 포함)와 로컬 PGlite로 앱을 띄우고, 인터뷰 30문답 이상(건너뛰기·취소 섞어서), 인터뷰 중 회차 점검 동시 실행, 자동 저장 동시 진행을 자동 스크립트로 돌리며 서버 프로세스 생존과 메모리를 관찰한다. `next dev`와 `next start` 둘 다 본다.
- 재현되면 원인을 고치고 회귀 테스트를 남긴다. 재현되지 않으면 시도한 시나리오와 관찰 결과를 보고서에 남긴다. 어느 쪽이든 B·D의 변경(Server Action 줄 막힘 제거, 시간 제한)이 "먹통" 증상의 직접 원인을 없앤다.

### F. UX

- 승인 안내 문구: 인터뷰 페이지 설명, 끝내기 확인창, 끝낸 뒤 안내를 실제 동작에 맞춘다. 요지: "답 아래에서 바로 승인하거나 거절할 수 있습니다. 처리하지 않은 후보는 승인 대기에 남습니다."
- 회차 제목: 저장되는 제목에는 "{n}화" 접두어를 넣지 않는다. 새 회차 기본 제목은 빈 문자열이다. 원고 가져오기에서 제목 줄이 "{n}화 …"이면 접두어를 뗀 나머지를 제목으로 쓰고, 제목 줄이 없으면 빈 제목이다. `chapterLabel`은 제목이 그 회차 번호의 "{n}화"(또는 "제{n}화")로 시작하면 그 접두어를 떼고 붙인다(기존 데이터 보호). 기존 행은 마이그레이션으로 정리한다(제목이 정확히 "{n}화"면 빈 문자열, "{n}화 …"면 접두어 제거).
- 목표 분량: 회차를 완료로 바꿀 때 글자 수(공백 포함, 편집기 진행률과 같은 기준)가 작품의 목표 분량보다 적으면 확인창을 띄운다. "목표 5,500자 중 4,265자(78%)입니다. 그래도 완료할까요?" 집필 화면과 회차 목록 양쪽에 적용한다. 서버는 막지 않는다. (설계 판단)
- 관계 그래프: 그래프 화면에 cytoscape 인스턴스가 정확히 하나만 붙는지 E2E로 확인한다(노드 층 캔버스 1장). 하나면 코드는 그대로 두고 보고서에 "정상 구조(층 3장)"로 적는다. 둘 이상이면 원인을 고친다.

## 6. 제약

- Next.js 16 규칙(CLAUDE.md): route handler가 AI를 부르면 `maxDuration = 300`, `params`는 Promise.
- 사용자에게 보이는 문구는 짧고 쉬운 한국어. 식별자와 주석은 영어.
- 서비스는 `AppError`를 던지고, 액션과 route는 `ActionResult`를 돌려준다. 비회원은 항상 `NOT_FOUND`.
- 구조화 출력 zod 스키마 제약(min/max/regex/default/optional 금지) 유지.
- 테스트는 실제 AI를 부르지 않는다.
- 패키지 변경 금지.
