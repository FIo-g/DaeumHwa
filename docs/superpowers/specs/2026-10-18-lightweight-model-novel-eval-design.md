# 경량 모델 품질 평가 하네스 (소설 5화) 설계

작성: 2026-10-18 · 기획 Opus · 구현 Haiku · 검토 Sonnet

## 1. 왜 하는가

다음화의 AI 기능은 인터뷰, 설정 추출, 연속성 검사, 맞춤법, 독자 시뮬레이션, 연재 조언, 문체 제안, 초안으로 여러 개다. 사용자는 앱에 있는 이 기능들 **전부를 경량 모델만으로 출판할 수 있는 수준까지** 끌어올리고 싶어 한다. 추천 화면에서는 기획에 프론티어 모델을 권하겠지만, 경량 모델에게 기획이나 검토를 맡겨도 충분해야 한다.

이번 작업은 그 첫 단계다. 지금 상태에서 각 모델이 어디서 부족한지를 같은 조건으로 측정해 기록한다. 개선은 기록을 본 사용자가 다음 작업으로 지시한다.

- 로컬 경량 모델이 Haiku·Luna(클라우드 경량 모델)와 비슷한지, 못 미치면 어디가 얼마나 못 미치는지 본다.
- 한국어판과 영어판을 같은 내용으로 돌려서, 실패가 모델 실력 탓인지 한국어 탓인지 가린다.
- 하네스는 저장해 두고, 나중에 모델이나 프롬프트를 바꾼 뒤 같은 테스트를 다시 돌릴 수 있게 한다.

## 2. 목표, 비목표, 실패로 볼 것

**목표**
- 모델 5개 × 언어 2개, 총 10회 실행. 한 번 실행할 때마다 앱 기능을 거쳐 소설 5화를 만든다.
- 실행마다 Sonnet이 검토해 기능별 부족한 점과 근거를 기록한다.
- 10회를 비교하는 요약을 남긴다. 기능별 부족한 점, 개선 후보, 한국어와 영어 차이를 담는다.
- 하네스는 명령 하나(또는 저장 워크플로 하나)로 다시 돌릴 수 있다. 중간에 멈춘 실행은 그 지점부터 이어서 돌린다.

**비목표 (이번에 하지 않음)**
- 프롬프트나 코드 개선. 이번 라운드는 측정과 기록만 하고, 개선은 사용자 지시를 기다린다.
- API 키 연동 화면, 역할별 모델 선택 화면. 별도 프로젝트로 이 작업 다음에 브레인스토밍한다.
- 로컬 모델을 제품 화면에서 고르는 기능.
- 원고 가져오기(import) 기능 평가.

**실패로 볼 것 (돌아가도 실패)**
- AI가 앱 기능을 거치지 않고 그냥 소설만 쓰는 테스트. 반드시 앱의 서비스 함수(`src/server/*`)를 거쳐야 한다.
- 모델 간 차이가 모델 실력이 아니라 작가 역할(Sonnet)의 변동이나 실행 조건 차이에서 나오는 테스트.
- 실행 도중 프롬프트나 코드를 고쳐서 앞 실행과 비교가 깨지는 것.
- 한 번 돌리고 다시 못 돌리는 하네스. 한도나 오류로 멈춘 뒤 처음부터 다시 해야 하는 하네스.
- 제품 동작이 바뀌는 것. 하네스를 위해 넣은 코드는 앱에서 쓰지 않으면 아무 영향이 없어야 한다.

## 3. 사용자가 정한 것

- 시험 모델은 5개다. 로컬 3개는 `qwen3.8:27b`, `gpt-oss:20b`, `exaone3.5:32b`이고, 모두 Ollama에서 MLX판으로 받는다. 클라우드 2개는 Haiku와 Luna다.
- MLX판이 없거나 받아지지 않으면 aside 브라우저(`aside-browser` 스킬)로 방법을 찾는다. 그래도 없으면 일반판을 받아 쓴다. 어떤 판을 썼는지 기록한다.
- 로컬 모델의 컨텍스트 길이, temperature, top_p, effort는 기획 단계에서 Opus가 쓸 수 있는 최선으로 정한다(아래 5절).
- 소설은 한국어판과 영어판을 같은 프롬프트, 같은 내용으로 각각 만든다. 목적은 한국어 탓인지 가리는 것이다.
- 한 모델이 하네스를 통해 5화를 끝내면 Sonnet이 검토해 부족한 점을 기록한다. 그다음 모델로 넘어가 5개 모델을 모두 끝낸다.
- 가능하면 로컬 모델 하나와 클라우드 모델 하나를 동시에 돌린다.
- 작가 역할은 Sonnet이 맡는다.
- 하네스는 저장해 두고 나중에 다시 테스트할 수 있게 한다.
- OpenCode Go 한도에 걸리면 Sonnet이 개입해 상태와 내용을 저장하고, 나중에 이어서 작업할 수 있게 한다.
- 모두 끝나면 결과를 기록해 두고 사용자의 다음 지시를 기다린다.
- 파이프라인 설계는 Opus가 한다.

## 4. 현재 환경 (2026-10-18 확인)

- 맥: Apple M5 Pro, 메모리 48GB, 디스크 여유 약 700GB.
- Ollama 0.32.14. 설치된 모델은 `qwen3.8:27b-mlx`(18GB), `qwen3-coder:30b`, `qwen3-coder-256k`다. gpt-oss와 exaone은 아직 없다.
- `.env.local`에는 `AI_PROVIDER`와 `OPENCODE_API_KEY`만 있다. Anthropic 키는 없다.
- OpenCode Go에서 쓸 수 있는 Claude 모델은 `claude-haiku-5-5` 하나다. Sonnet과 Opus는 없다. 그래서 Sonnet(작가, 검토)은 Claude Code 에이전트로 부른다.
- OpenCode Go 한도: 모델마다 월 한도가 있고(Go 요금제는 Haiku와 GPT Luna가 각 $15), 5시간 단위로 그 20%, 주 단위로 50%까지 쓸 수 있다.
- 앱의 일일 AI 토큰 한도는 기본 300만이다(`AI_DAILY_TOKEN_LIMIT`). 하네스에서는 끈다.
- 기존 평가 도구 `eval/run-continuity.ts`가 있다. 메모리 DB에 예제 작품을 넣고 서비스 함수를 직접 부르는 방식이고, 이번 하네스도 같은 방식을 따른다.

## 5. 시험 모델과 설정

| 모델 | 어디서 | 모델 id (예정) | 생각/effort | 샘플링 |
|---|---|---|---|---|
| Qwen3.8 27B | Ollama, MLX | `qwen3.8:27b-mlx` (설치됨) | 생각 모드 켬 | Qwen 권장값(생각 모드용) |
| gpt-oss 20B | Ollama, MLX 우선 | 확인 필요 | reasoning effort high | OpenAI 권장값 |
| EXAONE 3.5 32B | Ollama, MLX 우선 | 확인 필요 | 생각 모드 없음 | LG 권장값 |
| Haiku 5.5 | OpenCode Go | `claude-haiku-5-5` | effort 최대(게이트웨이가 거부하면 기존 대체 경로) | 보내지 않음 |
| GPT 6 Luna | OpenCode Go (Responses) | `gpt-6-luna` | reasoning effort 최대 | 보내지 않음 |

- **effort (사용자 지시):** 모든 작업을 그 모델이 지원하는 최대 effort로 돌린다. 제품의 작업별 effort(medium/high)를 하네스에서만 덮어쓴다. 실행 설정에 적힌 값과 실제로 적용된 값을 둘 다 기록한다.
- **컨텍스트 길이 (설계 판단):** 모델 자체의 최대치를 넘지 않는 선에서, 이 맥 48GB에 올라가 안정적으로 도는 가장 큰 값을 쓴다. 준비 단계에서 모델마다 한 번 측정해 실행 설정에 기록한다. 하네스에서 가장 긴 입력과 최대 출력을 합친 길이보다 작으면 그 자체를 발견 사항으로 기록한다.
- **temperature, top_p (설계 판단):** 최대로 올리면 문장이 무너지므로, 각 모델 제작사가 품질용으로 권장하는 값을 쓴다. 정확한 숫자는 구현 단계에서 공식 문서(모델 카드)로 확인해 실행 설정에 적는다.
- **출력 길이:** 생각 모드가 있는 모델은 생각 토큰도 출력 한도를 먹는다. 생각 때문에 답이 잘리지 않게 출력 한도를 넉넉히 잡는다. 그래도 잘리면 기록한다.
- **시간 제한 (설계 판단):** 로컬 모델은 느리다. 하네스는 시간 제한을 넉넉히 늘려 실행이 끝까지 가게 하고, 단계마다 걸린 시간과 "제품 기본 시간 제한이었으면 멈췄을지"를 기록한다.
- **Ollama 운용 (설계 판단):** 메모리 때문에 로컬 모델은 한 번에 하나만 올린다. 동시 요청도 하나만 처리하게 해서, 연속성 검사와 설정 추출이 병렬로 들어와도 차례로 처리되게 한다.
- **Luna (설계 판단):** OpenCode Go의 Luna 두 개(`gpt-6-luna`, `gpt-5.6-luna`) 중 최신인 `gpt-6-luna`를 쓴다.

## 6. 하네스 구조

### 6.1 구성 요소

1. **하네스 프로그램** `eval/novel/`
   - 앱의 서비스 함수를 직접 부르며 한 회 실행을 진행한다.
   - 시험 대상 모델이 모든 AI 작업을 맡는다.
   - 작가 판단이 필요한 지점에 오면 질문 파일을 쓰고 멈춘다. 답 파일이 생기면 이어서 진행한다.
   - 실행 명령은 `pnpm eval:novel`(가칭)이다.
2. **Ollama 클라이언트**
   - 앱의 `AiClient` 인터페이스(`src/ai/types.ts`)를 구현해 Ollama 로컬 모델을 부른다. 구조화 출력과 스트리밍을 지원한다.
   - 이번에는 하네스에서만 쓰고 제품의 공급자 선택에는 연결하지 않는다(설계 판단). 다음 프로젝트인 API 키 연동에서 다시 쓸 수 있게 `src/ai/` 아래에 둔다.
   - 새 패키지는 쓰지 않는다.
   - **공정성 (설계 판단):** 로컬과 클라우드의 차이가 클라이언트 코드 차이에서 나오면 안 된다.
     - 구조화 출력은 공급자 자체 기능(Ollama의 JSON 스키마 형식 지정)을 쓴다. 클라우드 클라이언트가 각 공급자의 구조화 출력을 쓰는 것과 같은 취지다.
     - 그 뒤의 처리(zod 검증, JSON 지시문 대체, 실패 시 재시도 횟수와 방식)는 기존 클라이언트(`AnthropicAiClient`)와 같은 정책을 따른다. 가능하면 같은 코드를 쓴다.
     - 정책이 달라지는 부분이 생기면 실행 설정에 적는다.
3. **평가용 래퍼 클라이언트**
   - 시험 대상 클라이언트를 감싸서 다음 일을 한다.
     - effort를 최대로 덮어쓴다.
     - 시간 제한을 늘린다.
     - 영어판에서 시스템 프롬프트를 영어판으로 바꾼다.
     - 모든 호출의 입력, 원문 출력, 파싱 결과, 토큰, 시간, 재시도, 오류를 기록한다.
   - 제품 코드에 손대야 한다면 앱이 쓰지 않을 때 아무 영향이 없는 최소한의 연결 지점만 둔다.
4. **Sonnet 작가**
   - Claude Code 에이전트(`model: 'sonnet'`)다.
   - 비공개 설정집과 작가 지침을 보고 질문 파일에 답한다.
   - 산문을 쓰거나 모델 출력을 고쳐 쓰지 않는다.
5. **Sonnet 검토자**
   - Claude Code 에이전트다.
   - 끝난 실행의 기록물을 읽고 검토서를 쓴다. 10회가 끝나면 비교 요약을 쓴다.
6. **저장 워크플로** `.claude/workflows/novel-eval.js`(가칭)
   - 위 흐름 전체를 돌린다.
   - 인자로 모델 목록, 언어 목록, 이어하기 여부를 받는다. 기본값은 5개 모델 × 2개 언어다.
   - 끝난 실행은 건너뛰고, 멈춘 실행은 이어서 돌린다.

### 6.2 실행 상태와 이어하기

- 실행마다 폴더 하나를 쓴다(`eval/results/novel/<runId>/`).
- DB는 메모리가 아니라 그 폴더 안의 파일 기반 PGlite를 쓴다. 그래야 작가 답을 기다리는 동안 프로세스가 끝나도, 한도로 멈췄다가 다음 날 다시 시작해도 상태가 남는다.
- 단계 하나가 끝날 때마다 진행 위치(`state.json`)와 기록물을 저장한다. 다시 시작하면 마지막으로 끝난 단계 다음부터 간다.
- 작가와의 주고받기는 파일로만 한다. 하네스가 `pending.json`(무엇을 묻는지, 판단에 필요한 자료)을 쓰면, 작가가 `answer.json`을 쓴다. 하네스는 답의 형식을 검사하고, 틀리면 다시 묻는다.

### 6.3 한 회 실행의 흐름

**준비**
1. 실행 폴더와 빈 DB를 만들고, 실행 설정을 기록한다. 설정에는 모델, 판, 샘플링, 컨텍스트, effort, 커밋 해시, 언어가 들어간다.
2. 테스트 사용자와 작품을 만든다. 작품 제목과 목표 분량은 설정집에서 가져온다.
3. 실제 작가가 화면에서 직접 입력하는 것만 작가 쪽 서비스로 미리 넣는다(설계 판단).
   - 표기 규칙(`createNamingRule`)
   - 계획된 떡밥(`createThread`, 계획됨 상태). 설정 추출이 계획된 떡밥을 제대로 이어받는지 볼 수 있다.
   - 회차 제목
   - 인물, 장소, 사실, 관계, 회차 요약은 넣지 않는다. 이것들은 인터뷰와 설정 추출 제안을 거쳐서만 위키에 들어가고, 바로 이 과정이 측정 대상이다.

**문체** (계획 단계에서 바꿈)
- 문체 제안(`suggestStyleCard`)은 저장된 회차에서 그 인물의 대사를 3줄 이상 모아서 만든다. 그래서 1화 전에는 쓸 수 없다.
- 작품 문체 카드는 설정집의 견본으로 작가가 직접 넣는다. 준비 단계에서 넣는다.
- 인물 문체 제안은 2화가 끝난 뒤 주요 인물마다 돌린다. 작가가 받아들인 카드는 3~5화 초안에 쓰인다.

**인터뷰 (1화 전)**
- 인터뷰를 시작한다(`startInterview`). 질문을 받고(`askNextQuestion`), 작가가 설정집에 근거해 답한다(`answerTurn`).
  - 질문을 설정 중심으로 할지 이야기 중심으로 할지는 질문 모델이 스스로 고른다(계획 단계에서 확인). 하네스는 12개를 묻고 비율을 기록한다.
- 답할 때마다 그 답에서 나온 제안을 작가가 승인하거나 거절한다(`approveProposal`/`rejectProposal`). 이걸로 위키가 처음 채워지고, 다음 질문이 늘어난 위키를 보고 나온다.

**회차 루프 (1~5화)**
1. (2화부터) 연재 방향 조언(`runDirectionAdvice`)을 돌린다. 작가는 고정된 줄거리와 맞는 선택지가 있는지만 기록한다. 조언은 다음 지시문에 반영하지 않는다.
2. 초안을 쓴다(`startDraft`).
   - 지시문은 설정집에 고정된 그 화의 지시문이다. Sonnet이 새로 쓰지 않는다.
   - 초안 맥락에 넣을 위키 항목은 정해진 규칙으로 고른다. 결과는 기록한다.
   - 작가는 초안이 쓸 수 없는 상태인지 판단한다. 비었거나, 잘렸거나, 다른 언어거나, 본문이 아닌 말이 섞인 경우다. 그러면 실제 작가처럼 다시 쓰게 한다(최대 2번, 설계 판단).
   - 끝까지 쓸 수 없으면 가장 나은 시도를 회차로 저장하고, 그 사실을 기록한 뒤 다음 단계로 간다.
   - 다시 쓴 횟수와 이유는 그 모델의 약점으로 기록한다.
3. 맞춤법(`runProofread`)을 돌린다. 작가가 제안을 하나씩 수용하거나 거절하고, 수용한 것만 본문에 반영한다.
4. 회차를 저장하고 완료로 표시한다(`createChapterFromDraft`, `saveChapter`, `setChapterStatus` 등 앱이 실제로 쓰는 경로).
5. 회차 검사(`runChapterCheck`)를 돌린다. 표기 규칙, 연속성 검사, 설정 추출이 이때 함께 돈다.
6. 작가가 판단한다.
   - 연속성 지적: 맞는 지적인지 헛지적인지 판단하고 앱에서 처리한다.
   - 설정 제안: 회차 요약 제안을 포함해 승인하거나 거절한다.
7. 독자 시뮬레이션(`runReaderSimulation`)을 돌린다.

**마무리**
- 최종 위키를 저장하고 실행 상태를 `done`으로 바꾼다.

- 앞 화에서 잘못 승인되거나 빠진 설정은 다음 화의 맥락에 그대로 쌓인다. 실제 사용과 같은 조건이고, 이것도 측정 대상이다.
- 단계의 정확한 함수 이름과 순서는 앱이 실제로 쓰는 경로를 따른다. 위 이름은 확인한 서비스 함수 기준이다.

### 6.4 작가(Sonnet)의 판단 규칙

작가 지침 파일에 적어 두고 모든 실행에 똑같이 쓴다.

**변동을 줄이는 장치 (설계 판단)**
- 작가는 어떤 모델을 판정하는지 모른다. 질문 파일에 모델 이름을 넣지 않는다.
- 작가 판단 한 번마다 새 Sonnet 에이전트를 부른다. 각 에이전트에는 같은 설정집, 같은 지침, 그 실행에서 지금까지 내린 판단 요약을 준다. 한 세션이 길어지며 생기는 흔들림을 막고, 어느 판단에서 멈춰도 이어서 할 수 있다.
- 인터뷰 답변은 설정집의 **답변 은행**에서 가져온다. 답변 은행은 주제별로 미리 써 둔 답이다. 작가는 질문에 맞는 답을 골라 거의 그대로 쓰고, 질문에 맞춰 이어 붙이는 말만 더한다. 그래서 같은 주제를 물으면 어느 모델이든 같은 답을 받는다.
- 다시 돌렸을 때 비교 가능하다는 것은 같은 설정집, 같은 지침, 같은 답변 은행으로 Sonnet이 판단한다는 뜻이다. 결정적인 자동 판정기는 만들지 않는다(설계 판단). 판단 기록은 모두 남아서 검토자가 의심스러운 판단을 짚을 수 있다.

**판단 규칙**
- **인터뷰:** 답변 은행과 설정집에 있는 내용만 답한다. 없는 것은 "아직 정하지 않았다"고 답한다. 질문이 잘못됐거나 이미 답한 걸 또 물으면 그 사실도 기록한다.
- **설정 제안:** 설정집과 맞고 형식이 바른 것(이름이 온전하고, 주어가 맞고, 중복이 아닌 것)만 승인한다. 틀린 것은 거절하고 이유를 남긴다.
- **맞춤법:** 실제 오류를 고치는 제안만 수용한다.
- **연속성 지적:** 설정집이나 승인된 위키와 실제로 어긋날 때만 맞는 지적으로 본다.
- **문체 카드:** 견본 문단의 문체를 잘 담았으면 받아들인다. 판단 이유를 남긴다.
- **금지:** 산문을 쓰거나 모델 출력을 고쳐 쓰지 않는다. 회차 지시문을 바꾸지 않는다.
- 모든 판단은 이유와 함께 `author-decisions.jsonl`에 남는다. 검토자가 이걸 근거로 쓴다.

### 6.5 영어판

- 영어판 실행에서는 모델이 받는 글이 전부 영어여야 한다(설계 판단). 일부만 바꾸면 한국어와 영어가 섞여서 "한국어 탓인지" 가리는 목적이 흐려진다. 영어로 옮길 것:
  - 설정집, 견본 문단, 회차 지시문, 답변 은행, 작가 지침
  - 앱의 AI 시스템 프롬프트. "모든 출력은 한국어로 쓴다" 같은 언어 지시도 영어로 바꾼다.
  - 프롬프트 조립 코드에 박힌 한국어 문구. 예: "(없음)", "약 N자", "주제:", "질문:", "승인 대기"
  - 설정 맥락 묶음의 항목 이름표. 예: `renderContextPack`의 종류와 인물 필드 이름
  - 독자 시뮬레이션 페르소나
- 바꿔 끼우기는 평가용 래퍼 클라이언트에서 한다(계획 단계에서 바꿈). 제품 코드에는 언어 연결 지점을 두지 않는다.
  - 모든 AI 호출은 작업 이름을 달고 클라이언트를 지나간다. 래퍼는 그 이름으로 시스템 프롬프트를 영어판으로 바꾸고, 완성된 프롬프트 안의 한국어 문구를 정해진 표로 영어로 옮긴다.
  - 영어 문구는 모두 하네스 쪽(`eval/novel/localize/`)에 있다. 제품 코드에는 영어 문구가 들어가지 않는다.
  - 테스트로 막을 것: 제품 프롬프트에 새 한국어 문구가 생기면, 영어판 변환 뒤에 한글이 남는 것을 테스트가 잡는다.
  - 실행 중에 걸러 낼 것: 호출마다 변환 뒤 남은 한글 수를 기록한다.
- 번역은 규칙을 빼거나 더하지 않는 충실한 번역이어야 한다. 구현 후 Sonnet이 한국어판과 대조해 확인한다.
- 맞춤법 작업은 영어판에서 영어 맞춤법과 문법을 본다.
- 한국어 전용 코드(조사 처리 같은 결정적 규칙)는 그대로 둔다. 영어에서 맞지 않게 동작하면 발견 사항으로 기록한다.
- 목표 분량은 한국어 목표 분량에 맞먹는 영어 글자 수로 정한다. 견본 문단의 한국어와 영어 글자 수 비율로 맞춘다(설계 판단).

### 6.6 OpenCode Go 한도와 오류

오류를 두 갈래로 나눈다(설계 판단).

**모델 실패: 기록하고 계속**
- 구조화 출력이 계속 깨지거나, 형식은 맞는데 내용이 비는 경우다. 다시 해도 또 날 가능성이 큰 실패다.
- 이런 실패에 멈추면 실행이 끝없이 돌고, 뒤 기능은 측정되지 못한다.
- 앱 자체 재시도가 끝난 뒤 하네스가 그 단계를 한 번 더 시도한다. 그래도 실패하면 단계를 `failed`로 기록하고 다음 단계로 간다. 예를 들어 설정 추출이 실패한 화는 제안 없이 넘어간다.
- 초안은 6.3의 다시 쓰기 규칙을 따른다.
- 이 실패는 그 모델의 핵심 약점으로 검토서에 들어간다.

**외부 장애: 멈추고 이어하기**
- OpenCode Go 한도, 네트워크 오류, Ollama가 죽은 경우, 프로세스 중단이다. 모델 탓이 아니고, 나중에 다시 하면 되는 실패다.
- 하네스가 한도 오류(429나 한도 문구)를 받으면 그 단계를 끝내지 않은 채 상태를 저장한다. 그리고 `paused-limit` 상태로 멈춘다.
- 워크플로에서 Sonnet이 개입해 실행 폴더에 `RESUME.md`를 쓴다. 들어갈 내용은 다음과 같다.
  - 어느 실행이 어느 단계에서 멈췄는지
  - 오류 원문
  - 언제쯤 다시 될지(5시간 창 기준)
  - 이어서 돌리는 명령
- 그동안 다른 줄(로컬 모델)은 계속 돈다. 한도로 멈춘 실행은 나중에 워크플로를 이어하기로 다시 돌릴 때 그 단계부터 다시 시작한다.
- 네트워크 오류, Ollama 중단, 프로세스 중단도 같은 방식으로 `paused-error`로 멈추고 기록한다.
- 같은 단계에서 외부 장애로 세 번 멈추면 그 실행을 `blocked`로 두고 요약에 적는다. 그 줄의 다음 실행으로 넘어간다.
- 앱이 원래 하는 재시도와 대체 경로 안에서 해결된 실패는 멈추지 않고 기록만 한다. 그것도 모델의 약점이기 때문이다.
- 로컬 모델의 시간 초과는 하네스가 시간 제한을 넉넉히 늘린 뒤의 이야기다. 늘린 한도까지 넘으면 모델 실패로 본다.

### 6.7 실행 순서와 병렬

**먼저 시험 운행 (설계 판단)**
본 실행 전에 세 단계로 시험한다.
1. 가짜 클라이언트로 5화 전체를 돌려 흐름을 확인한다.
2. qwen3.8 한국어로 1화만 실제로 돌려 걸리는 시간을 잰다.
3. Haiku 한국어로 1화만 돌려 토큰과 비용을 잰다.

잰 값으로 본 실행 전체의 시간과 OpenCode Go 사용량을 추정해 기록하고 본 실행에 들어간다. 시험 운행 결과는 본 실행 결과에 섞지 않는다.

대략 추정은 이렇다. Haiku 한 번 실행(5화)에 입력 60만, 출력 12만 토큰 안팎이고, 최대 effort의 생각 토큰을 더하면 그보다 커진다. 그래서 5시간 창에 한 번 걸릴 수는 있지만 월 한도 안에는 들어갈 것으로 본다. 시험 운행에서 이 추정이 크게 틀리면 그 숫자를 사용자에게 보고하고 진행한다.

**본 실행**
- **로컬 줄:** qwen3.8 한국어 → qwen3.8 영어 → gpt-oss 한국어 → gpt-oss 영어 → exaone 한국어 → exaone 영어
- **클라우드 줄:** Haiku 한국어 → Haiku 영어 → Luna 한국어 → Luna 영어
- 두 줄을 동시에 돌린다. 실행끼리는 폴더와 DB가 따로라서 공유하는 것이 없다.
- 실행 하나가 끝나면 바로 Sonnet 검토를 붙인다. 검토가 다른 실행을 기다리지 않는다.
- 10회 실행과 검토가 모두 끝나면(또는 남은 것이 한도로 멈춘 것뿐이면) 비교 요약을 쓰고 멈춘다.

## 7. 설정집 (고정 입력)

- 기존 평가용 예제 작품 "잿빛 종루의 열쇠"(`eval/fixtures/continuity/work.json`)의 세계관을 다시 쓴다(설계 판단). 인물 8명, 사실 25개, 떡밥 4개, 표기 규칙이 이미 있다.
- 그 폴더의 회차 본문은 일부러 오류를 넣은 것이라 쓰지 않는다. 세계관과 1~5화 줄거리만 가져온다.
- 기존 사실 중 6화 이후에 해당하는 것은 빼고, 1~5화 범위로 다듬는다.
- 기존 줄거리는 한 문장짜리라서 초안 지시문으로 쓰기엔 짧다. 계획 단계에서 Opus가 회차별 지시문과 정답 요약을 새로 쓴다.
- 설정집에 들어갈 것:
  - 작품 개요와 장르
  - 인물(말투 메모 포함), 장소, 사실(유효 회차 범위 포함), 떡밥(계획 회차 포함), 표기 규칙
  - 문체 견본 문단 한두 개
  - 답변 은행: 인터뷰에서 나올 만한 주제별 답. 인물, 세계, 갈등, 결말 방향 등 설정과 이야기 양쪽을 덮는다.
  - 1~5화 고정 지시문: 그 화에서 일어나야 할 사건을 작가가 초안 화면에 적는 정도로, 몇 문장에서 한 문단 길이
  - 1~5화의 정답 요약
- 목표 분량은 한국어 회차당 5,000자 안팎이다(설계 판단: 웹소설 한 화 기준).
- 설정집은 작가만 본다. 시험 대상 모델은 인터뷰 답변과 회차 지시문으로만 이 내용을 접한다.
- 위치: `eval/fixtures/novel/ko/`, `eval/fixtures/novel/en/`

## 8. 기록물

**실행 폴더** `eval/results/novel/<runId>/` (이미 gitignore됨)
- `config.json`: 모델, 판, 설정, 커밋 해시, 시작·끝 시각
- `state.json`, `db/`, `pending.json`, `answer.json`
- `calls/NNN-<task>.json`: 호출마다 시스템, 입력, 원문 출력, 파싱 결과, 토큰, 시간, 재시도, 오류
- `chapters/01.md` ~ `05.md`: 저장된 최종 본문. 맞춤법 반영 전 초안도 함께 남긴다.
- `wiki-final.json`, `author-decisions.jsonl`, (멈췄으면) `RESUME.md`

**커밋하는 기록** `docs/eval/novel/<날짜>/`
- `<model>-<lang>.md`: 실행별 Sonnet 검토서
- `summary.md`: 10회 비교 요약
- 원문 기록이 커서 gitignore된 폴더에 있으므로, 검토서와 요약은 근거를 인용해 혼자 읽어도 이해되게 쓴다.

## 9. 검토 기준 (Sonnet)

실행별 검토서는 같은 틀로 쓴다. 기능마다 1~5점, 근거 인용, 부족한 점, 개선 후보를 적는다.

| 항목 | 보는 것 |
|---|---|
| 초안(출판 가능성) | `docs/eval/novel-quality-criteria.md`의 기준표를 쓴다. 회차마다 문턱 T1~T7, 품질 Q1~Q9(1~5점), 출판 가능·우수 판정을 매긴다. 5화 전체에는 설정 모순 누계와 TTCW 통과율(참고)을 적는다 |
| 인터뷰 | 질문이 쓸모 있는지, 같은 질문 반복, 주제가 엇나가는지, 답에서 설정을 제대로 뽑았는지 |
| 설정 추출·제안 | 원천 글 대비 빠진 것과 틀린 것. 특히 이름 잘림("전직 시계탑 수리공 노은하"류), 주어 뒤바뀜(한기준/한시우류), 같은 인물 중복 카드 |
| 연속성 검사 | 맞는 지적과 헛지적의 비율, 놓친 오류 |
| 맞춤법 | 맞는 제안과 틀린 제안의 비율 |
| 독자 시뮬레이션·연재 조언 | 본문에 근거했는지, 쓸모 있는지 |
| 문체 제안 | 견본 문체를 담았는지 |
| 운영 | 구조화 출력 실패, 재시도, 시간 초과(제품 기준), 단계별 시간과 토큰 |

- **추출 채점의 기준 (설계 판단):** 설정 추출과 인터뷰 추출은 설정집 전체가 아니라 그 추출이 실제로 읽은 원천 글로 채점한다. 원천 글은 작가의 인터뷰 답, 저장된 회차 본문이다. 묻지 않아서 나오지 않은 설정은 모델 탓이 아니다. 설정집과 어긋나는지는 따로 본다. 원천 글에는 맞게 뽑았지만, 그 원천(모델이 쓴 초안)이 설정집과 어긋난 경우가 여기에 해당하고, 이건 초안의 문제로 기록한다.
- **기준선:** Haiku와 Luna의 결과를 목표선으로 본다. 로컬 모델은 그 대비로 평가한다.
- **비교 요약에 담을 것:**
  - 10회 점수표
  - 기능별로 로컬 모델이 Haiku·Luna에 못 미치는 지점
  - 한국어와 영어 차이로 본 원인 진단
  - 개선 후보 목록: 프롬프트, 작업 쪼개기, 자기 검토, 코드 검증, 설정 조정 등. 예상 효과 순으로 정렬한다.

## 10. 제약

- `CLAUDE.md`의 규칙을 따른다.
  - 테스트에서 실제 API를 부르지 않는다.
  - 서비스는 `AppError`를 던지고 액션은 던지지 않는다.
  - 위키 변경은 승인을 거친다.
- 패키지를 추가하거나 바꾸지 않는다.
- 하네스는 `--fake` 모드를 둔다. 가짜 클라이언트와 가짜 작가로 흐름 전체를 끝까지 돌리는 테스트를 만들고, 이 테스트는 `pnpm test`에서 돈다. 이어하기와 한도 멈춤도 가짜로 테스트한다.
- `pnpm typecheck`, `pnpm lint`, `pnpm test`가 통과해야 한다.
- 제품 동작은 바뀌지 않는다. 한국어 프롬프트, 작업별 effort, 시간 제한, 일일 한도 기본값을 그대로 둔다. 하네스 실행 중에만 덮어쓴다. 제품 코드에 넣는 연결 지점은 시간 제한 덮어쓰기(`src/ai/run.ts`) 하나뿐이다. effort와 영어판은 래퍼 클라이언트가 맡는다.
- 역할 분담은 사용자가 정한 방식을 따른다. 구현은 Haiku, 검토는 Sonnet, 작가와 실행 검토도 Sonnet이다.
- 공개 저장소에 push하는 것은 사용자에게 먼저 묻는다.

## 11. 구현하는 사람에게 맡기는 것

- CLI 모양, 파일 형식, 폴더 안의 세부 이름
- Ollama를 어떤 API로 부를지(자체 API, OpenAI 호환, Anthropic 호환)와 구조화 출력 방식. 컨텍스트 길이 같은 옵션이 실제로 적용되는지는 확인해야 한다.
- 영어 프롬프트로 바꿔 끼우는 방법. 단, 제품 동작은 바뀌지 않아야 한다.
- 워크플로가 오래 걸리는 단계(로컬 초안은 수 분 이상)를 어떻게 기다릴지. 에이전트나 명령의 시간 제한 때문에 실행이 죽지 않아야 한다.
- 샘플링 권장값의 정확한 숫자, 컨텍스트 측정 절차
- 초안 맥락에 넣을 위키 항목을 고르는 규칙의 세부
- 인터뷰 질문 수의 미세 조정

## 12. 설계 판단 목록 (Opus가 정한 것, 확인 부탁)

1. temperature와 top_p는 "최대"가 아니라 제작사 권장값을 쓴다. 컨텍스트와 effort는 최대로 둔다.
2. Sonnet은 OpenCode Go에 없어서 Claude Code 에이전트로 부른다.
3. 회차 지시문은 고정한다. 작가(Sonnet)는 답변과 승인 같은 판단만 하고 글은 쓰지 않는다.
4. 연재 조언 결과는 기록만 하고 다음 지시문에 반영하지 않는다.
5. 설정집은 기존 예제 작품 "잿빛 종루의 열쇠" 세계관을 쓴다. 회차당 5,000자 안팎이다.
6. Luna는 `gpt-6-luna`를 쓴다.
7. Ollama 클라이언트는 `src/ai/`에 두지만 제품 공급자 선택에는 아직 연결하지 않는다.
8. 원문 기록은 gitignore 폴더에 두고, 검토서와 요약만 `docs/eval/novel/`에 커밋한다.
9. 원고 가져오기 기능은 이번 평가에서 뺀다.
10. 인터뷰는 질문 12개로 한다. 설정과 이야기 중 무엇을 물을지는 질문 모델이 고르고, 하네스는 비율을 기록한다.
11. 영어판은 모델이 받는 글을 전부 영어로 바꾼다. 바꿔 끼우기는 래퍼 클라이언트가 하고, 영어 문구는 하네스 쪽에만 둔다.
12. 모델 실패(계속 깨지는 출력)는 기록하고 다음 단계로 간다. 외부 장애(한도, 네트워크, Ollama 중단)만 멈추고 이어서 한다.
13. 쓸 수 없는 초안은 최대 2번 다시 쓰게 하고, 그래도 안 되면 가장 나은 것을 저장하고 기록한다.
14. 작가는 판단마다 새 에이전트를 부르고, 어떤 모델인지 모른다. 인터뷰 답은 미리 쓴 답변 은행에서 가져온다.
15. 표기 규칙, 계획된 떡밥, 회차 제목만 작가 쪽에서 미리 넣는다. 나머지 설정은 인터뷰와 추출로만 들어간다.
16. 추출은 설정집 전체가 아니라 실제로 읽은 원천 글을 기준으로 채점한다.
17. Ollama 클라이언트는 기존 클라이언트와 같은 검증과 재시도 정책을 쓴다.
18. 본 실행 전에 시험 운행을 한다. 가짜로 5화, qwen 1화, Haiku 1화를 돌려 시간과 비용을 잰다.
19. 작품 문체 카드는 작가가 설정집 견본으로 직접 넣고, 인물 문체 제안은 2화 뒤에 돌린다.
