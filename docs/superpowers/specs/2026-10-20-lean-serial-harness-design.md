# 가벼운 클라우드 모델용 연재 하네스 설계

작성: 2026-10-20 · 기준 코드: `feat/ai-improvement-round2` b97853e · 조사: Haiku가 Aside 브라우저로 5개 분야(오픈소스, 논문, 작가 의도, 비용, 상용 도구)를 찾음 · 설계: Opus

## 1. 의도

사용자(서비스 운영자)의 말:

- 배포는 클라우드 모델로 한다. 로컬 모델은 품질 개선과 테스트용이다.
- Haiku와 Luna는 솔직히 강한 모델이 아니다. 이런 경량 클라우드 모델이 잘 짜인 하네스 안에서 비용을 아끼면서 최고의 품질을 내는 것이 목표다.
- 가장 좋은 하네스는 시간과 비용을 덜 쓰고, 몇 번의 지시 없이도 작가가 원하는 방향으로 글을 써서 완성해 준다.
- 작가는 고칠 것이 적고, 작가의 요구 사항은 바로바로 잘 적용된다. 그것이 작가의 만족도를 올린다.

이 문서는 그 목표를 이루기 위한 하네스 전체 설계다. "하네스"는 모델 둘레의 모든 것이다. 문맥 묶음, 작업 순서, 프롬프트, 코드 점검, 수정 루프, 작가 화면의 흐름, 측정을 포함한다. 모델 자체는 바꾸지 않는다.

## 2. 지금 상태

### 2.1 품질 (R2a, 1화, 2026-10-20)

| 실행             | 판정      | Q 평균 | 걸린 문턱          |
| ---------------- | --------- | ------ | ------------------ |
| Haiku 5.5 한국어 | 출판 불가 | 3.44   | T3 분량(22자 부족) |
| Haiku 5.5 영어   | 출판 가능 | 3.89   | 없음               |
| Luna 6 한국어    | 출판 불가 | 3.22   | 없음               |
| Luna 6 영어      | 출판 불가 | 3.33   | 없음               |

1라운드부터 반복해서 나온 약점은 다음과 같다.

- 분량 미달
- 인물 말투가 비슷함(Q5)
- 계기 없는 감정 변화(Q4)
- 같은 박자의 장면 반복
- 보여 주기 대신 설명(Q3)
- 약한 회차 끝(Q9)
- 가끔 설정 모순

R2a는 P 묶음(장면 수, 결정과 대가, 첫 장면 목표, 계획된 떡밥 표시 등) 이전 코드다. P 묶음의 효과는 아직 재지 않았다(R2b).

### 2.2 비용과 시간 (R2a 기록에서 계산)

한 화 기준이다. 작품당 한 번 하는 인터뷰는 뺐다. 단가는 Haiku 5.5와 GPT-6 Luna 모두 입력 $0.10, 출력 $0.50(100만 토큰당, 2026-10-20 공식 가격 페이지)이다.

| 실행         | 호출 | 입력 토큰 | 출력 토큰 | 모델 시간 | 비용   |
| ------------ | ---- | --------- | --------- | --------- | ------ |
| Haiku 한국어 | 8    | 47,606    | 64,189    | 283초     | $0.037 |
| Haiku 영어   | 8    | 32,392    | 48,535    | 220초     | $0.028 |
| Luna 한국어  | 9    | 33,871    | 28,296    | 295초     | $0.018 |
| Luna 영어    | 9    | 26,145    | 21,033    | 239초     | $0.013 |

- 인터뷰는 작품당 $0.014~0.021이다.
- 비용의 85% 이상이 출력 토큰이다. Haiku 한국어 초안 호출 하나가 출력 13,848토큰을 썼는데, 남은 본문은 약 5,200자다. 같은 분량에 Luna는 4,297토큰을 썼다. Haiku 출력의 상당 부분은 생각 토큰으로 보인다(추정, 클라우드 기록에는 생각 길이가 없다).
- 이 숫자는 eval 설정 기준이다. 서비스와 설정이 다르다.

  | 설정           | eval           | 서비스                                                                                             |
  | -------------- | -------------- | -------------------------------------------------------------------------------------------------- |
  | effort         | 모든 작업 high | 작업마다 다름. 질문 생성·문단 다듬기·이어 쓰기 low, 대부분 medium, 초안·연속성 검사·방향 조언 high |
  | 출력 한도 하한 | 32,000         | 작업 값                                                                                            |

  `--product-limits`는 한도만 맞추고 effort는 high로 둔다. 그래서 지금은 **실제 배포 설정의 품질과 비용을 잰 적이 없다.**

### 2.3 이미 있는 기능

- **설정 위키:** 인물, 장소, 규칙, 사실, 떡밥, 회차 요약, 문체 카드(작가 예문과 `rules`)
- **문맥 묶음:** 예산 글자 수 안에서 위키를 고른다.
- **인터뷰:** 작품을 처음 만들 때 한다.
- **초안:** `startDraft`. 작가 지시, 목표 분량, 고른 위키 항목을 받아 한 번에 스트리밍한다. 짧으면 이어 쓰기를 한다. 코드 점검으로 분량 계획, 문단 다듬기, 문장 고치기, 외래 문자를 본다.
- **저장 뒤:** 연속성 검사, 사실 추출 제안(작가 승인), 맞춤법, 독자 시뮬레이션, 2화부터 방향 조언
- **다듬기(P6):** 미리 보고 적용한다.
- **있지만 클라우드 서비스에서 꺼진 것**
  - 두 단계 초안(장면 계획 → 본문)과 장면 다시 쓰기: 로컬과 eval 전용
  - 인물 말투 기능: `AI_SPEECH_STYLE` 환경 변수로 끔
- **프롬프트 캐시:** Anthropic 경로의 시스템 블록에만 `cache_control`이 붙는다.

## 3. 핵심 판단

1. **돈은 이미 싸다. 비싼 것은 작가의 시간이다.**
   - 한 화 API 비용은 2~4센트, 100화를 써도 4달러 아래다.
   - 작가가 실제로 치르는 비용은 지시를 쓰는 시간, 기다리는 시간, 다시 생성하는 횟수, 고치는 시간이다.
   - 그래서 하네스는 **"작가가 그대로 쓰는 첫 원고"**를 최우선으로 노린다. 다시 생성할 때마다 비용과 시간이 통째로 한 번 더 든다.
2. **돈을 줄일 곳은 출력, 특히 생각 토큰이다.** 입력 캐시는 입력이 비용의 15% 아래라 효과가 작다. 작업별 effort 조정이 가장 큰 손잡이다.
3. **약한 모델은 계획을 주면 낫다.** 계획 후 쓰기는 연구에서 가장 일관된 이득이다(Agents' Room, AgentWrite, Re3, DOC). 계획을 작가가 고칠 수 있게 보여 주면 작가는 본문보다 훨씬 싼 곳에서 방향을 잡는다(Dramatron, Typetak, Sudowrite).
4. **작가 요청은 한 번 말하면 계속 지켜져야 한다.** 작가 불만 1순위는 "지시를 무시함", "개요와 설정을 잊음", "모두 같은 말투"다(Sudowrite 피드백 게시판, r/WritingWithAI). 요청을 일회성 입력란에 두면 실패한다(Sudowrite "Extra Instructions"). 저장되고, 보이고, 작가가 고칠 수 있는 요청 목록이어야 한다(NovelAI Author's Note, CIPHER).
5. **고칠 곳만 고친다.** 전체를 다시 쓰지 않는다. 코드 점검(무료) → 값싼 점검 1회 → 걸린 장면만 다시 쓰기. 여러 후보를 만들어 고르는 방식(best-of-N)은 경량 모델 판정이 약하다는 연구가 있어(LitBench) 기본으로 쓰지 않는다.

## 4. 목표, 하지 않을 것, 실패로 볼 것

### 목표

- **G1 품질:** 배포 설정 그대로(작업별 effort와 한도) Haiku와 Luna가 한국어 1화에서 출판 가능(T1~T7 통과, Q 평균 3.75 이상, 2점 이하 없음). 영어는 그다음이다(설계 판단: 사용자는 한국 웹소설 작가다).
- **G2 적은 지시:** 작가가 한 줄 이하(빈칸 포함)로 회차를 시작할 수 있다. 하네스가 위키, 떡밥, 지난 화, 방향 조언으로 회차 계획을 먼저 제안한다.
- **G3 적은 수정:** 작가가 고칠 곳이 적다. eval에서는 검토자가 "작가라면 반드시 고칠 곳" 수를 세고, 서비스에서는 AI 초안과 저장본의 차이 비율을 센다(8절).
- **G4 요청 유지:** 작가가 한 번 말한 요청이 이후 모든 회차에 적용되고, 지켜졌는지 확인된다.
- **G5 비용과 시간 (사용자 결정: 품질 우선, 상한만):**
  - 한 화 비용은 단계 0 배포 설정 기준선의 2배까지 허용한다(여전히 몇 센트).
  - 그대로 쓰기를 누른 뒤 본문 첫 글자까지의 시간은 기준선(쓰기를 누른 뒤 첫 글자)보다 길어지지 않는다.
  - 계획 시간은 20초 이내를 목표로 한다(설계 판단).

### 하지 않을 것

- 모델 학습이나 미세 조정, 보상 모델 학습
- 더 큰 모델로 바꾸기, 로컬 모델 품질 올리기(로컬은 시험대로만 쓴다)
- 작가 없이 여러 화를 자동으로 쓰는 기능
- 임베딩 검색 인프라 새로 들이기(위키가 커져 필요해지면 따로 설계)

### 실패로 볼 것 (기술적으로 돌아가도)

- AI가 위키를 직접 바꾼다. 작가가 모르는 규칙이 몰래 쌓인다.
- 계획 카드나 요청 목록 때문에 작가가 해야 할 클릭과 입력이 오히려 늘어난다.
- 품질을 올리려고 호출이 계속 늘어 한 화 시간이 두 배가 된다(Re3식 재순위, 다중 후보 루프).
- 아직 밝히지 않은 비밀이 문맥에 들어가 본문에 새어 나온다.
- 효과를 재지 않은 프롬프트 변경이 클라우드 기본 경로에 들어간다.

## 5. 제약

- **배포 모델:** OpenCode 게이트웨이를 거친 경량 클라우드 모델(Haiku 5.5, GPT-6 Luna 급)이다. 게이트웨이가 캐시와 배치를 넘겨주는지는 확인해야 한다(9절).
- **CLAUDE.md 규칙:**
  - AI는 위키를 직접 쓰지 않는다. 위키 변경은 작가 행동이나 승인된 제안에서만 나오고 `change_log`를 남긴다.
  - 사용자 문구는 한국어다.
  - 서비스는 `AppError`, 액션은 `ActionResult`를 쓴다.
  - 테스트는 `FakeAiClient`만 쓴다.
  - 패키지 추가는 오케스트레이터와 정한다.
- **클라우드 기본 경로 변경 규칙:** 바꿀 때마다 같은 조건의 전후 측정을 한다. 효과가 없거나 나빠지면 되돌린다.
- **DB 마이그레이션:** 필요하면 한다. 2라운드의 금지는 그 라운드에만 해당했다.

## 6. 설계

### 6.1 회차 흐름 (작가가 보는 것)

```
[다음 화] ─▶ 회차 계획 카드 (AI 제안, 몇 초)
               - 장면 3~6개: 목표, 결정과 대가, 감정의 계기, 장소, 인물, 목표 글자 수
               - 회차 끝 장치(질문, 위기, 반전 중 하나)
               - 이번 화에 움직일 떡밥
               - 적용될 작가 요청 (요청 장부에서)
            ─▶ 작가: 그대로 쓰기 / 한 줄 고치기 / 장면 빼기·순서 바꾸기
            ─▶ 본문 스트리밍 (장면 표시, 장면별 분량)
            ─▶ 자동 점검 (코드 → 값싼 점검 1회)
            ─▶ 걸린 장면만 고친 안을 미리 보기 (적용 / 버리기)
            ─▶ 저장 → 연속성 검사, 사실 추출 제안, 요약 (뒤에서)
```

- 작가가 첫 줄에 지시를 적으면 계획 카드가 그 지시를 반영한다. 비워 두면 위키와 지난 화로 제안한다.
- **계획 카드가 기본 흐름이다 (사용자 결정).** 지금의 "지시 적고 바로 쓰기"는 버튼 하나로 남긴다(빠른 길).
- 빠른 길에도 요청 장부, 코드 점검, 점검 1회는 그대로 적용한다. 장면 표시와 장면별 분량은 계획이 있을 때만 쓰고, 빠른 길은 지금처럼 회차 전체 분량 계획을 쓴다.
- eval은 기본 흐름(계획 카드)을 잰다.

### 6.2 회차 계획 카드 (계획 후 쓰기를 서비스로)

- eval 전용이던 `draft-beats`(P1 장면 수, P2 결정과 대가, P3 장소)를 클라우드 서비스로 올린다. 카드에 넣을 항목은 아래와 같다.
  - **감정의 계기:** 장면에서 인물 감정이 바뀌면 무엇 때문인지 적는다(Q4 약점).
  - **장면 역할:** 도입, 전환, 고조, 회차 끝 중 하나(Agents' Room의 역할 구분을 호출 하나로 줄임). 같은 역할이 연달아 오면 계획 단계에서 경고한다(장면 반복 약점).
  - **회차 끝 장치:** 마지막 장면은 요약하지 않고 질문, 위기, 반전 중 하나로 끝낸다(Q9 약점, "AI가 회차를 결론문으로 닫는다"는 작가 불만).
  - **장면별 목표 글자 수:** 분량 계획(`draftLengthPlan`)에서 나눈다.
- 계획 호출은 작고 싸야 한다. 문맥 묶음의 요약판과 effort low~medium으로 시작하고, 측정으로 정한다.
- 카드는 그 회차의 실행 기록에 남는다. 위키가 아니다. 작가가 카드를 고친 내용은 요청 장부 후보가 될 수 있다(6.3).

### 6.3 작가 요청 장부

작가가 한 번 말한 것을 계속 지키게 하는 장치다.

- **요청 하나에 들어가는 것**
  - 문장(예: "세린은 누구에게나 반말", "'심장이 쿵' 금지", "회차 끝은 대사로")
  - 범위: 작품 전체, 특정 인물, 이번 화만
  - 종류: 문체, 말투, 금지 표현, 분량, 내용
  - 출처: 작가가 직접 씀, 고쳐 쓰기 지시, 작가 수정에서 추론
  - 상태: 제안됨, 적용 중, 끔
- **들어오는 길 세 가지**
  1. 작가가 직접 쓴다(요청 목록 화면, 또는 계획 카드의 "앞으로도 이렇게" 체크).
  2. 작가가 장면 고쳐 쓰기나 다듬기에 준 지시 중 회차를 넘어 지켜야 할 것을 AI가 요청으로 제안한다. 작가가 승인한다.
  3. 작가가 AI 초안을 고친 내용에서 AI가 규칙을 추론해 제안한다(CIPHER). 이것은 마지막 단계에 넣는다. 추론된 규칙이 "간결하게" 같은 막연한 말로 흐르는 실패가 알려져 있어서, 막연한 제안은 버린다.
- **적용**
  - 적용 중인 요청은 계획, 초안, 이어 쓰기, 장면 고쳐 쓰기, 다듬기 프롬프트에 항상 들어간다(고정 블록, 캐시 앞부분).
  - 범위가 인물이면 그 인물이 나오는 장면에만 넣는다.
- **확인**
  - 코드로 확인할 수 있는 것은 코드로 본다: 금지 표현, 반말과 존댓말, 분량.
  - 나머지는 6.5의 점검 1회에서 함께 본다.
  - 어긴 곳은 걸린 장면 고치기로 넘긴다.
- **기존 문체 카드의 `rules`와 인물 말투 필드와의 관계는 빌더가 정한다.** 조건은 하나다. 작가가 "지금 적용 중인 요청 전부"를 한 화면에서 볼 수 있어야 한다.

### 6.4 장면 단위 분량과 문맥

- **분량:** 본문은 장면 표시를 달고 장면별 목표 글자 수를 따른다. 남은 글자 수를 알려 주는 방식(카운트다운 표시)은 GPT-4.1에서 분량 준수율을 30% 미만에서 95% 이상으로 올렸다는 결과가 있다. 경량 모델에서는 검증되지 않았으므로 먼저 잰다.
- **한 번에 쓰기와 장면마다 쓰기**
  - 한 번에 쓰기: 지금 방식. 호출이 적고 장면 사이가 매끄럽다.
  - 장면마다 쓰기: 장면별 분량을 지키기 쉽고, 한 장면만 다시 쓸 수 있다. 입력은 장면마다 다시 보내지만 캐시를 쓰면 싸다.
  - 둘을 eval에서 비교해 고른다(8절). 기본 가정은 한 번에 쓰고, 짧은 장면만 이어 쓰는 것이다(설계 판단).
- **문맥 묶음 규율** (NovelCrafter, Sudowrite에서 가져옴)
  - 위키 항목마다 "항상 넣음 / 언급되면 넣음 / 넣지 않음" 단계를 두고, 예산이 모자라면 정해진 순서로 뺀다. 요청 장부와 문체는 절대 빼지 않는다.
  - 아직 밝히지 않을 사실(공개 회차가 정해진 비밀)은 그 회차 전까지 문맥에서 뺀다. 스토리 바이블이 미스터리 답을 문단마다 흘린 사례가 보고되었다.
  - 인물마다 대표 대사 2~3줄을 둔다. 작가 예문에서 이번 장면의 인물과 감정에 가까운 대목을 골라 2~3개 넣는다(무작위가 아니라 골라서). Q5 말투 약점을 겨냥한다. 꺼져 있는 말투 기능(`AI_SPEECH_STYLE`)은 이 설계에 합쳐 측정 후 켠다.
  - 위키 항목 설명은 짧게 유지하도록 안내한다. 긴 외모 묘사는 모델이 반복해서 집어 쓴다는 보고가 있다.
- **캐시를 위한 순서:** 시스템, 요청 장부, 문체, 항상 넣는 항목을 앞에 고정한다. 회차 계획과 언급된 항목은 뒤에 둔다. 그래야 한 화의 여러 호출과 같은 작업 세션의 다음 화가 앞부분을 캐시로 읽는다.

### 6.5 값싼 점검과 국소 수정

1. **코드 점검 (호출 없음)**
   - 이미 있는 것: 분량, 문단 길이, 외래 문자, 반복 어절(P8 문단 첫 어절)
   - 새로 넣는 것
     - 장면별 분량
     - 금지 표현: 작가 요청과 공통 상투어 목록
     - 같은 n-그램 반복
     - 마지막 문단이 요약문인지
     - 인물별 반말과 존댓말
     - 비밀 누출: 공개 전 사실의 핵심어
2. **점검 호출 1회 (값싼 설정)**
   - 측정된 약점에 맞춘 짧은 채점표만 본다: 핵심 순간을 설명으로 넘김, 계기 없는 감정 변화, 같은 박자 반복, 회차 끝 장치, 요청 위반.
   - 장면 번호와 이유만 돌려준다. 원문을 다시 쓰지 않는다.
3. **걸린 장면만 다시 쓰기 1회**
   - 이미 있는 장면 다시 쓰기(D 트랙, 지금은 로컬 전용)를 클라우드로 연다. 한 화에 1회까지다.
   - 결과는 다듬기(P6)처럼 미리 보고 적용한다. 작가가 버리면 원래 초안이 그대로 남는다.
4. **여러 후보 고르기는 하지 않는다.** 회차 끝 장면만 두 후보로 쓰는 것은 측정 항목으로 남긴다.

### 6.6 비용과 시간 손잡이

- **배포 설정 측정 모드(전제 조건):** eval이 작업별 effort와 한도를 서비스와 똑같이 보내는 옵션을 만든다. 이후 모든 비교는 이 모드로 한다.
- **effort:** 작업마다 low, medium, high를 바꿔 가며 재서, 품질이 떨어지지 않는 가장 낮은 값을 고른다. 생각 토큰이 비용의 대부분이라 가장 큰 손잡이다. 계획, 점검, 추출은 낮게 시작한다.
- **캐시:** 6.4의 고정 앞부분에 캐시 표시를 단다(Haiku 5.5 캐시 읽기 $0.01, 최소 512토큰, 기본 5분 유지). 작업 세션이 길면 1시간 유지(쓰기 단가 2배)를 비교한다.
- **배치:** 작가가 기다리지 않는 저장 뒤 작업은 배치 API(50% 할인)를 검토한다. 사실 추출, 독자 시뮬레이션, 연속성 검사 일부가 대상이다. 게이트웨이가 지원할 때만 한다. 결과가 늦게 와도 되는지는 단계 4에서 사용자와 정한다.
- **캐시 경로:** Haiku는 Anthropic 형식, Luna는 Responses 형식으로 게이트웨이를 지난다. 두 경로의 캐시 방식이 다르므로 따로 확인하고 따로 잰다.
- **기록:** `ai_runs`에 이미 있는 토큰 수에 캐시 읽기와 쓰기 토큰을 더하고, eval 요약에 한 화 비용(달러), 첫 글자까지 시간, 총 시간을 낸다.
- **시간을 세는 법** (설계 판단)
  - **계획 시간:** 다음 화를 누른 뒤 계획 카드가 뜰 때까지
  - **본문 첫 글자:** 그대로 쓰기를 누른 뒤 첫 글자가 보일 때까지. 작가가 카드를 읽는 시간은 넣지 않는다.
  - **총 모델 시간:** 한 화에 쓴 모든 호출 시간의 합. 저장 뒤 작업은 따로 적는다.

### 8.2 실행 규칙

- 모든 비교는 배포 설정 모드로 한다. 모델은 Haiku와 Luna, 언어는 한국어 먼저다. 영어는 결과만 적고 채택을 가르지 않는다(설계 판단).
- **eval 실행은 두 종류다** (설계 판단)
  - **비교 실행:** 지금처럼 작가 에이전트가 설정집의 회차 지시 전체를 준다. 계획 카드가 있으면 그대로 승인만 한다. Q와 문턱을 기준선과 비교하는 데 쓴다.
  - **적은 지시 실행:** 작가 에이전트가 한 줄(설정집 회차 지시의 첫 문장)로 시작한다. 계획 카드를 설정집 개요와 `mustInclude`에 맞을 때까지 고친다. 고친 횟수와 글자 수가 G2 지표다. `mustInclude` 누락은 T1로 그대로 센다. 기준선(계획 카드 없음)은 한 줄 지시로 바로 쓴다.
- **G4 요청 심기** (설계 판단)
  - 심을 요청 넷은 설정집의 문체 규칙과 겹치지 않게 새로 정한다. 예: 조연 하나의 말버릇, 금지 표현 둘, 회차 끝 방식 하나.
  - 작가 에이전트가 1화에서 한 번만 말한다. 기준선에서는 1화 지시문에, 새 흐름에서는 요청 장부에 쓴다. 2화와 3화에서는 말하지 않는다.
  - 기준선이 2화부터 못 지키는 것은 설계상 맞다. 그것이 지금 서비스의 실제 동작이다.
- **effort 조정** (설계 판단)
  - 보조 작업(계획, 점검, 추출, 연속성 검사)은 소설 전체 실행 대신 작업 단위 시험으로 고른다. 정답이 있는 기존 세트(`eval/fixtures/continuity*`, 저장된 실행의 호출 입력)를 low, medium, high로 다시 돌려 비교한다.
  - 초안과 장면 고쳐 쓰기의 effort만 소설 실행으로 고른다.
- **기본 모델:** 단계 0 기준선을 보고 하나를 고른다. 이후 단계의 반복 실행은 그 모델로만 하고, 다른 모델은 단계 끝에 한 번 확인한다(설계 판단).
- **남은 2라운드 실행** (설계 판단)
  - R2b와 R2l: 단계 0 기준선으로 대신한다.
  - R2t(두 단계 초안): 단계 1의 비교에 들어간다.
  - R2s(말투 기능): 단계 2의 문맥 규율에 들어간다.
  - R2c "후": 싸고 짧아서 단계 0에서 그대로 돌린다.
- 1화 한 번은 우연을 가르지 못한다(R2a 요약의 판단). 채택을 정하는 비교는 같은 조건을 두 번 돌리거나 3화로 돌린다. 요청 유지(G4)는 3화 실행으로만 잰다.
- **채택 규칙** (설계 판단, 9절에서 확정)
  - Q 평균이 0.1 넘게 떨어지지 않는다.
  - 문턱 실패가 늘지 않는다.
  - 품질, 개입 수, 고칠 곳 수, 비용, 시간 중 하나 이상이 나아진다.
  - 비용과 시간은 G5 상한 안에 있다.
- **단계마다 실행 6개 (사용자 결정).** 1화 실행 2개에 Claude Code 에이전트 토큰이 약 550만이므로, 단계당 약 1,500만 토큰이다.
  - 기본 모델 한국어 비교 실행 2회
  - 기본 모델 한국어 적은 지시 실행 1회
  - 기본 모델 한국어 3화 실행 1회. 3화 실행은 1화 실행 약 3개 몫이지만 1개로 센다. 단계 2(요청 유지)에서만 필수다.
  - 다른 모델 한국어 확인 1회, 기본 모델 영어 확인 1회
  - 작업 단위 effort 시험은 이 예산 밖이다. 호출 몇 개라 싸다.
  - 단계 0은 기준선이라 두 모델 모두 한국어와 영어를 잰다(실행 4개 + 반복 2개).

| 3 점검과 국소 수정            | 6.5. 클라우드 장면 다시 쓰기. 상투어와 반복 점검                                                                                           | 고칠 곳 수, 다시 생성 수                                                |
| 4 학습하는 요청과 비용 손잡이 | 수정에서 요청 추론(CIPHER), 예문 고르기, 배치, 1시간 캐시                                                                                  | 요청 유지, 비용                                                         |

R2b(2라운드 "후" 측정)는 단계 0의 기준선과 겹친다. 단계 0을 R2b 대신 하는 것이 효율적이다(설계 판단). 2라운드 계획서의 R2b는 effort high 기준이라 1라운드와 비교할 때만 의미가 있다.

## 10. 정해진 것과 남은 것

**사용자가 정한 것**

- 배포는 경량 클라우드 모델이다. 로컬은 시험대다.
- 목표는 적은 시간과 비용, 적은 지시, 작가 방향대로 완성, 적은 수정, 요청의 즉시 적용과 유지다.

**설계 판단 (빌더가 바꿔도 됨, 바꾸면 이유를 적는다)**

- 한국어 먼저, 영어는 그다음
- 한 번에 쓰기를 기본 가정으로 두고 비교로 확정
- best-of-N 보류
- 수정에서 요청 추론은 마지막 단계
- 채택 규칙의 0.1
- R2b 대신 단계 0

**빌더에게 맡기는 것**

- 요청 장부의 데이터 모양: 새 테이블인지, 문체 카드나 인물 필드 확장인지
- 계획 카드의 화면 배치
- 점검 채점표의 문구
- 상투어 목록의 출처
- 캐시 표시 위치
- 장면 표시 형식

- eval 실행 두 종류(비교, 적은 지시), 요청 심기 방법, 작업 단위 effort 시험, 단계 0 뒤 기본 모델 선택, 남은 2라운드 실행 정리, 시간 세는 법 (8.2, 6.6)

**사용자가 정한 것 (2026-10-20 확인)**

- 비용과 시간: 품질 우선, 한 화 비용은 기준선의 2배까지, 본문 첫 글자까지 시간은 늘리지 않음
- eval 예산: 단계마다 실행 6개
- 계획 카드가 기본 흐름, 바로 쓰기는 버튼으로 남김
- 서비스 사용 지표를 모은다. 집계 숫자만 저장하고 본문은 저장하지 않는다. 작가에게 무엇을 세는지 한국어로 알린다.

**빌더가 먼저 확인할 것:** 게이트웨이(OpenCode)가 두 경로에서 캐시와 배치를 넘겨주는지
